## 1. 原则

用户 11-27 的原话：“本插件只是辅助agent进行工作,只是对工作流进行引导,记录工作中产生的内容, 不让插件的行为卡住agent做事.”

10-30 初版已经写过同样的意思：“通用内核只做少量可靠检查”“日常执行有充分自主权”“首版不建设通用多智能体调度系统”；“每增加一条规则，都要回答：它避免了哪种已观察到的损失，能否由较短的任务说明或确定性工具解决”。

落到实现上是四条：

1. **工作靠 agent 自己的命令往前走。** 任何一个组件停下，都不应让整个研究停下。交出工作的那条命令负责让下一个会话知道（3.2）。
2. **插件不替 agent 决定能不能做。** 不设名额，不设并发上限，不设超时阶梯。唯一保留的次数限制是每轮审核最多两次（用户定，第 6 章）。它防的是过度审核，不挡工作：两次之后，作者照常往下走。
3. **CLI 只拒绝记不下来的事。** 另外只有一件要加 `--force --reason`：合并提交上的测试失败了，仍要移动主线（5.1）。其余流程规则一律照做，同时打印提醒、在记录上留标记，由审核者、协调者和用户看到后判断（第 5 章）。
4. **插件只做两件事：引导和记录。** 引导靠启动包、角色卡、待办，以及每条命令之后的下一步提示。记录靠数据库。

## 3. 结构

### 3.1 组成

| 部分 | 做什么 | 它停了会怎样 |
|---|---|---|
| `rl` 和数据库 | 记录；只拒绝记不下来的事；遇到流程问题，提醒并留标记；输出下一步提示；交接时打开或叫醒对方（3.2） | 没有它就没有记录。只有它是核心 |
| 会话 | 一个角色做一件事，对应 herdr 里一个标签页中的 agent（Claude Code、Codex 或 pi） | 会话之间互不影响 |
| hooks | SessionStart：告诉 agent 它是谁，先读 `rl pack`。Stop：结束回合前，把还没告诉它的新事项交给它（3.2）。UserPromptSubmit（只用于协调者）：用户说话时附上新事项 | 少了补送，推送照常 |
| 观察者 `rl watch`（可选） | 只读：重画研究页；补送命令没送到的事项，等太久的再提醒一次；报告停在对话框里的会话（3.4） | 少了补送、提醒和研究页的自动刷新：没送到的事项，要等对方下次说话或看待办 |

### 3.2 交接：谁的命令叫醒谁

一件事交给另一个会话时，由做这件事的命令当场通知对方。

| 命令 | 谁运行 | 通知谁（对方会话没开就先打开） |
|---|---|---|
| `rl task release T-x` | 协调者 | 假设、阶段任务通知 scientist-T-x；公共准备任务通知 researcher-T-x；带 `--to scientist` 时通知 scientist-T-x |
| `rl task dispatch T-x` | 科学家 | researcher-T-x |
| `rl task block T-x` | 研究者 | 任务的创建者；公共准备任务已经交给科学家时，通知那位科学家 |
| `rl task answer T-x` | 科学家 | researcher-T-x |
| `rl task deliver T-x` | 研究者、科学家 | 任务的创建者（科学家或协调者）。公共准备任务不等人验收：完成检查通过，交付时 CLI 就验收、合并（旧设计 6.4 节），再照 `rl task accept` 那一行通知 |
| `rl task return T-x` | 接收方 | 持有者 |
| `rl task accept T-x` | 创建者、协调者 | 依赖 T-x 的任务的创建者或持有者（前置已验收） |
| `rl task cancel T-x` | 创建者、协调者 | 持有者：只在它正忙、会话关不掉时，告诉它任务已取消 |
| `rl task claim T-x`（接手，3.3） | 创建者、协调者 | 原来的持有者：任务已被收回 |
| `rl review request` | 作者 | reviewer-RV-x：新的一轮就打开会话，复审或改目标就叫醒同一个会话 |
| `rl review answer` | 审核者 | 作者 |
| `rl discuss`、`rl reply` | 审核者和作者；被提问的会话 | 对方 |
| `rl question` | 协调者 | 被提问的会话 |
| `rl request` | 科学家；协调者（给用户的批准请求，7.2） | 协调者。协调者发给用户的不通知会话：进用户的待办，由协调者当面问 |
| `rl request answer` | 协调者 | 发请求的科学家 |
| `rl advise ask` / `rl advise answer` | 科学家 / 顾问 | advisor-AD-x / 科学家 |
| `rl run ended` | 执行器或提交者 | 提交者（当运行这条命令的不是提交者本人时） |
| `rl run usage` | 研究者 | 用量越过一条线时，通知假设任务的持有者；越过最高一条线时，同时通知协调者 |
| `rl decide --final` | 科学家 | 依赖这个假设的其他假设，其任务的持有者（上游变了） |

通知按对方会话的状态分六种情况：

1. **对方开着、空闲。** 往它的 pane 里打一行，格式同现在：`[smooth-research] <类型> <主记录>: <要做的事> — <说明>`。记进它会话记录的 `told`。
2. **对方开着、在忙。** 不打字。等它结束回合时，Stop hook 查出还没告诉它的事项，用 `decision: block` 加一行原因让它接着做，并把这些事项记进 `told`，同一件事不会再拦第二次，所以不会循环。`stop_hook_active` 为真时，只在接着做的这段时间里又来了新事项才拦，不然这些事项没人送。这只对 rl 打开的会话生效（环境里有会话名）。Claude Code 支持这种 hook；Codex 0.172 的二进制里有同样的字段和校验，实装前要试一次；pi 还没有接 rl 的 hook（第 13 章）。
3. **对方停在对话框。** 不打字。命令输出告诉调用者“X 停在对话框：<摘录>”，记进 X 的会话记录（`needs_decision`），再照本节的规则通知协调者，因为对话框由它处理（3.3）；X 是协调者自己时，留给用户，列在 `rl status` 里。
4. **对方没有开着的会话。** 打开它：有上次的宿主会话 id 就接着那段对话，第一行让它读 `rl pack`。打开是同步的，要等 agent 启动并回答文件夹信任问题，一般十几秒，最多约 90 秒。
5. **对方是协调者。** 协调者的 pane 也是用户的。用户在最近 `agents.user_quiet_minutes` 分钟内说过话，就不打字：新事项由 UserPromptSubmit hook 在用户下次说话时附上，或由 Stop hook 在协调者结束回合时交给它；用户安静下来以后，观察者补送（3.4）。
6. **以上都没送到**（herdr 不在、超时）。命令照样成功，输出“没能通知 X：<原因>；补救：`rl session open X` 或 `rl resume`”。

通知只是个指针，事实都在记录里，漏一次通知不会丢任何东西：观察者在跑时，下一拍补送（3.4）；不在跑时，对方下次 `rl inbox` 就能看到；谁有事却没开会话，用户在 `rl status` 里也能看到。

### 3.3 会话

- **名字**不变：`coordinator`、`scientist-T-x`、`researcher-T-x`、`reviewer-RV-x`、`advisor-AD-x`。
- **打开**有三种途径：
  - 3.2 表里的命令；
  - `rl session open NAME`，手动打开；
  - `rl resume`，一次性操作：先打开协调者，再打开所有有待办却没开着的会话，最后启动观察者。觉得哪里卡住了，随时可以跑一次。
- **持有者**：
  - 交接时直接写进任务：放行时给 3.2 表里通知的那个会话（假设、阶段任务给科学家，公共准备任务给研究者），派发给研究者，科学家新建的执行任务或准备任务给它自己。打开会话时不再替它认领。
  - 前置还没验收的任务，建好后先不分配，也不建工作树，因为分支要从已经合入前置的主线开出。前置验收时，`rl task accept` 通知创建者认领。想提前动手可以提前认领：会留标记，并提示前置合入主线后，把主线合进自己的分支。派发也照此处理。
  - `rl task claim` 还用来接手：创建者或协调者可以把任务收回（例如收回一个已经派发、但不该先跑的任务），并记下是从谁手里接过来的。
- **模型**：打开时按 `models.<role>` 选第一个可用的条目，剩余额度低的宿主排到后面。只在打开时选一次，不再关掉在用的会话换模型。配置每条命令都会重读，所以改了 `models`，下次打开会话就生效。
- **结束**：由让它的工作结束的那条命令关掉它，而且只关空闲的会话：
  - `rl task accept` 或 `cancel`：关掉这个任务的研究者，以及这个任务上各轮的审核者（任务结束，轮次也随之结束；没请复审的轮次不会自己结束）；
  - 协调者接收或取消假设任务、阶段任务时：关掉对应的科学家，以及它名下剩下的会话。
  其余情况下，会话留着也没关系，空闲时不花 token。`rl status` 会列出工作已结束但还开着的会话，用 `rl session close NAME` 关掉。
- **等待**：角色卡建议没事就结束回合，省 token。在等别人的结果时，对方的命令会叫醒它。在等自己的短作业时，可以自己等。插件不禁止等待。
- **对话框**：打开会话时，由 rl 回答文件夹信任问题（现有功能）。其他对话框由用户或协调者处理，`rl agent dialog` 和 `rl agent answer` 保留。
- **herdr**：仍然靠它开会话、送通知（11-25 第 46 项不变）。没有 herdr 时，命令照样记录，并打印手动打开会话的命令（`rl session open NAME --print`）。

### 3.4 观察者（可选）

`rl watch` 只读，只做三件事：

1. **重画研究页。** 记录变了，或每隔 `agents.page_minutes` 分钟，重画 `docs/research.html`（11-25 第 43、54 项不变）。没有观察者时，用 `rl view` 生成。页面过期时的横幅（现在是红色的“监视可能停了：运行 rl resume”）改为只说页面生成于何时、用 `rl view` 刷新，和下面去掉“watcher 没在跑”警告是同一个理由。
2. **补送和提醒。** 接收方开着且空闲时，还没告诉过它的事项下一拍打给它：命令没送到的，给协调者暂缓的，以及到点才出现的（例如作业过了预计结束时间还没有结果）。等得超过 `agents.deadlines` 的，再提醒一次，每件事只提醒一次。接收方没开会话的，不替它打开，只在 `rl status` 里列出。往协调者 pane 里打字的规则同 3.2。
3. **报告对话框。** 把停在对话框里的会话写进它的会话记录（`needs_decision`）。如果不是协调者自己的会话，就按第 2 条提醒协调者一次；协调者自己的对话框列在 `rl status` 里，留给用户处理。

它不改研究记录（任务、审核、决定、运行），不开会话，不认领，不关会话，不收尾合并，不换模型，不清上下文。它写的只有三样：会话记录里的 `told` 和 `needs_decision`、心跳文件、研究页。

`rl resume` 默认启动它。`rl status` 显示它在不在跑，只作信息；其他命令不再打印“watcher 没在跑”的警告。它的锁只为了防止两拍同时跑：抢不到锁就跳过这一拍，不退出（12 份记录之一）。每一拍都重读配置。

## 4. 待办和启动包

- 待办（`rl inbox`、启动包、`rl status`）照旧按规则从记录现算，只是一个视图。读它的有 agent、用户、Stop hook 和观察者的提醒。它不驱动打开会话、关闭会话这类动作，只有用户手动跑的 `rl resume` 按它打开有待办的会话（3.3）。
- **删掉**：超时阶梯（四级上报）、“等会话名额”、`timed`。已经等了多久照样显示。
- **修正**（对应 12 份记录中的两份）：讨论只在所在轮次还没结束时进待办，和 `rl reply` 的条件一致。轮次或任务结束后，它下面的审核结论和讨论不再出现。
- **前置还没验收的任务**：在持有者或创建者的待办里写明“在等 T-y”。前置验收时，由 `rl task accept` 通知（3.2）。
- **`rl doctor`**：新增反向检查，已结束的记录上不应再有待办。现有的检查（没结束的记录都有人在等）保留。
- **下一步提示**：原来有几项只靠 watcher 送，现在由命令输出的“下一步”提示补上。协调者接收最后一个假设任务时，提示阶段结束，以及复合假设的子假设都已收尾；记下用户的批准时，提示放行。

## 5. 检查：拒绝、强制和标记

### 5.1 三类

1. **拒绝：记不下来，或者会记错。**
   - 编号不存在，或记录类型不对；
   - 定义记录的参数缺失或格式错，例如假设任务的目标假设、执行任务的实验、裁决的状态、运行所属的任务；
   - 要封存或解析的文件不存在或解析不了，例如文档、实验清单、结果清单；
   - 要改写已记下的事实，例如封存的文档、最终决定、已有最终决定的假设命题。要改就新建修订或新记录；
   - 记下来会是假的：证据运行或准备运行时工作树有未提交的改动（记下的提交号和实际跑的代码对不上；试跑照旧不查）；结果清单的摘要对不上；审核者答复时带的提交或草稿不是这一次的目标（第 6 章）；
   - 并发：你读到的内容已经变了（例如验收时，任务刚被重新交付）。重读后再做。
2. **需要 `--force --reason`：会伤到共享的主线。** 只有一件事：合并提交上的测试失败了，仍要移动主线。强制会记成一条事件和一个标记。合并冲突不在此列：合并不了是事实，CLI 报告冲突、主线不动，由 agent 解决后重新交付。
3. **提醒和标记：其余所有流程规则。** 照做，在输出里打印提醒，在记录上写一个标记 `{code, text, at, by}`。标记会出现在四处：这个记录的 `rl show` 和核验行；接收方的启动包和待办说明；研究页；`rl status` 里给用户看的“没按流程做的事”一节。标记不阻止任何后续命令。

### 5.2 例子：现在的拒绝改成什么

| 现在拒绝的情况（函数） | 改为 |
|---|---|
| 用户还没批准树和排期就放行（`tasks.release`；它还要求答复以 “approve” 开头） | 放行不再检查批准。任务上有还没答复、或答复为 change 的批准请求时，照样放行，标记 `unapproved`，在 `rl status` 里给用户列出。批准改用明确的选项记录：`rl request answer RQ-x --by user --approve\|--change --text "<原话>"`；建树时的批准由 `rl tree record --approval` 一并记下；什么时候要问用户见 7.2 |
| 派发前测试没通过或没有记录（`tasks.dispatch`） | 照样派发，标记 `untested` |
| 没有审核覆盖这个提交，或者还有未关闭的方法类发现（`tasks.dispatch`、`reviews.covers`） | 照样派发，标记 `unreviewed` 或 `open-findings`。如果受保护范围自上次审核通过以来没变，在标记里注明。原来的快速通道因此不再需要 |
| 前置任务还没验收（原来不检查，研究者只能自己阻塞） | 照样派发，标记 `prerequisite`，研究者的任务卡上写明在等谁 |
| 交付时工作树有未提交的改动（`tasks._deliver_work`） | 交付已提交的部分，提醒还有未提交的改动 |
| 执行任务交付时没有证据；假设任务交付时没有最终裁决；假设任务的分支改了 `research/work/T-x/` 以外的文件（第 55 项） | 照样交付，各留一个标记 |
| 只有创建者能验收；协调者只能取消还在排队的任务；只有指定的会话能认领（`tasks.accept`、`cancel`、`claim`） | 照做，标记是谁做的 |
| 结论审核没通过就定稿（`research.finalize`） | 照样定稿，标记 `unreviewed` |
| 证据引用了试跑、偏离设计的运行或别的任务的运行（`research.add_evidence`）；证据运行在设计封存前或改版后登记（`runs.register`） | 照样记录，留标记 |
| 说明超过 300 字（`tasks._note`，这个上限是 11-10 用户定的） | 照样记录；通知和待办里只显示前 300 字，并打印提醒 |
| 试跑超过 `limits.trial_minutes`（`runs.register`） | 不再限制 |
| 在已结束的轮次里回复讨论（`messages.reply`） | 照样记录，但不再进待办 |
| 还在等待的复审不能改目标；轮次通过后，`dispatch` 提示复审，`review request` 却要求开新的一轮（`reviews._round`、`covers`） | 见第 6 章 |

实现时，把现有的拒绝逐条过一遍（`tasks.py` 70 处、`runs.py` 38 处、`research.py` 35 处、`reviews.py` 28 处、`messages.py` 9 处等），按 5.1 归类，结果作为附录补进本文。

## 6. 审核（11-27 用户定）

- **一轮审核**：一个作者、一个目标、一个审核者会话。目标是执行任务或准备任务的一个提交，或一份结论草稿。
- **每轮最多两次审核**：审核 → 修改 → 复审 → 修改。
  - 第一次审核就通过（没有未关闭的发现），这一轮就结束。
  - 复审之后，不管还剩什么，这一轮都结束。作者做完最后的修改，照常往下走；剩下的发现留在记录上，变成标记（第 5 章）。
  - 还想再审，就开新的一轮。
- **两次由同一个审核者会话完成**：复审时叫醒原来那个会话，它记得自己提过什么。这一轮结束前不关它；如果它的 pane 没了，就接着原来的宿主对话重新打开。
- **作者可以拒绝发现，但要写明理由**：`rl review reject RV-x#Fn --reason ..`，不需要审核者同意。复审时审核者看到理由，可以接受（发现关闭，记为撤回），也可以坚持（发现保持开放，标为有争议）。这条用来防止过度审核。
- **还在等待的那一次可以改目标**：审核者答复前，作者又提交了修改时，用 `rl review request T-x --recheck-of RV-x` 把这一次改到当前提交，不算新的一次，审核者会被叫醒。审核者答复时要带上它审的目标（`rl review answer RV-x --at <commit> ..`；结论审核带那份草稿的编号，改过的结论是一条新的草稿）。如果和当前目标不一致，就拒绝这次答复，免得结论落在它没看过的代码或草稿上。
- **发现的类别和严重度**：方法类、工程类和严重度都保留，用来写标记。
- **删掉**：
  - 科学家段和研究者段。研究者改了工程代码、想要审核时，开新的一轮；
  - 每段三次的上限，以及次数用完后升级到顾问裁决；
  - “只有审核者或裁决能关闭发现”；
  - `rl review settle`。
  顾问只在有人找时参与（`rl advise ask`）。
- **结论审核不带作者说明**（旧设计 6.3 节的规则）：改为角色卡里的建议。

## 7. 假设和任务

用户 11-27 看了 latent-branch-recovery-smr 的假设树后说：“latent-branch-recovery-smr 里,错误地把所有任务都拆成了假说,完全浪费了科学家的能力. 我的观点是, latent-branch-recovery-smr 里当前的状态理当只有一个假说,就是"H1 FHCS 在 CWQ 共同条件下同时胜过 DoG 和 CoG",其他只是为这个目标服务的任务”。插件的三条规则促成了这种拆法（第 2 章“假设树”一行）：计划的每一节都要有假设，根假设由子假设决定，排期以假设为单位。本章去掉前两条；第三条不变，一个假设仍配一个科学家，但假设只写研究判断以后，这位科学家负责整套检验（7.3）。同一天用户又定了三件事：建树不再是科学家的任务，改由协调者的子代理完成（7.2）；由裁决引出的新假设不用用户批准，除非预计超出一开始的预算（7.2）；检验计划由科学家自己决定，插件不另设记录（7.3）。

### 7.1 什么写成假设

假设是关于研究问题的判断：结果事先不确定，结论会改变路线，或者改变能主张的内容。和它竞争的解释也是假设，可以并列检验。10-30 初版 21.6 节记的那次端到端试跑就是这样：一个主假设，两个竞争解释先作候选。

为检验一个假设要做的其他事，都是它下面的任务：

| 内容 | 放在哪里 |
|---|---|
| 前提和工程：锁定数据、移植基线、把方法接到新数据上、显存、计费 | 准备任务：研究者写代码，带完成检查 |
| 要先跑一下才能定的设置：预算档、门限等超参数 | 执行任务：在开发集上校准，结果用来冻结检验方案 |
| 判定的组成部分，例如分别胜过每个对手 | 假设命题里的判定规则 |
| 机制对照：收益来自哪一步 | 主实验的臂和分析，结论写进裁决的 `--means`。裁决之后它若成了要回答的问题，再立为新假设 |
| 探索性的变体，例如换一种门限，结果单独报告、不参与主判定 | 主实验里多一个臂 |
| 扩大到下一规模的门槛 | 裁决之后的路线决定 |
| 有效性复核，例如基线有没有被移植削弱、按论文口径重算 | 执行任务，它的证据限定裁决的范围 |

假设树跟着结果长：裁决引出了新问题，才有新的假设。不照计划的目录预先拆。

### 7.2 建树：协调者的子代理（11-27 用户定）

用户 11-27 的原话：“我希望将拆树任务从科学家的职责里分出来, 拆树任务不需要任何角色, 只在一开始将如何从任意文档中提取假说,建立项目所需假说树的说明给协调者的subagent让它工作后返回给协调者.” 接着又说：“拆树任务,subagent用当前家族最好模型的xhigh. 然后也不能直接 rl hypothesis add 吧, 要是用户觉得不好要改怎么办”。

- 建树不再是任务，不开会话，不占任何角色。树审核随之去掉，把关的是用户：子代理只写草稿，用户看过、改到满意、批准以后，才记进记录。
- **说明**由 `rl tree prompt [--from <文档>...]` 打印，内容是：7.1 的规则；要读的文档，默认 `docs/plan.md`，也可以是任意别的文档；现有的树；草稿的格式；交回什么。这份说明只进子代理的上下文，不写进任何角色卡，协调者自己也不读。
- **模型**：子代理用协调者所在家族最好的模型，effort 为 xhigh。配置 `models.tree` 每个家族一条，默认 `claude:claude-fable-5-2@xhigh` 和 `codex:gpt-6.2-astra@xhigh`，出了更好的模型就跟着改。待办里建树那一项写明这次用哪个模型、哪个 effort。
- **草稿**放在项目里的 `research/tree-draft/`，不是记录：
  - `tree.yaml`：每个假设的标题、命题、范围、目的、出处（哪份文档的哪一节）、父节点、预计用量（`cost`），是主假设还是竞争解释，存疑标记（新颖性或可行性不够时的依据和选项，即 `rl hypothesis flag` 记的那种，不是第 5 章的流程标记）；为什么是这几个假设；几个假设共用的准备工作，每项带要求和完成检查；要问用户的事。
  - `rl tree check` 检查草稿的格式，只报告问题，不记录；它和 `rl tree record` 都默认读这个目录。`rl view` 把草稿画进研究页，标明是草稿，用户在页面上看全文。
- **步骤**：
  1. 还没有假设时，协调者的待办提示建树；已经有草稿时，改为提示请用户看草稿，免得协调者重启后又开一个子代理。协调者按提示的模型开一个子代理，只交代一句：“运行 `rl tree prompt`，照它做，把它要的摘要交回来。”
  2. 子代理读文档，写草稿，跑 `rl tree check` 直到没有问题，然后交回一段摘要：每个假设一行，存疑标记，共用的准备工作，要问用户的事。协调者的上下文里只多了这段摘要，文档全文不进去。
  3. 协调者运行 `rl view`，把草稿画进研究页（草稿不是记录，观察者不会因它重画），再按摘要向用户说明，全文请用户看研究页。用户要改，协调者再开一个同样的子代理，交代：“运行 `rl tree prompt`，按用户的意见改草稿：<用户原话>”。已有草稿时，`rl tree prompt` 的说明改为在草稿上修改，用户没提到的地方不动。草稿不是记录，改多少次都行。
  4. 用户批准后，协调者运行 `rl tree record --approval "<用户原话>"`，一次记下：假设，存疑标记，一条说明为什么是这几个假设的路线决定，共用的准备工作（建成排队的公共准备任务，要求和完成检查取自草稿），以及用户的批准。没带 `--approval` 时照样记下，标记 `unapproved`（第 5 章）。记好后删掉草稿目录，内容都在记录里了。
  5. 排期：为要检验的假设建假设任务；公共准备任务第 4 步已经建好，协调者放行即可。批准建树就是批准检验这些假设，放行它们的假设任务不再另要批准。以后由裁决引出的新假设不用用户批准，协调者直接排期、放行。用户 11-27 的原话：“由裁决引出的新假设不需要用户放行,除非预计计算资源消耗超过一开始的预算.” 所以只有预计会超出一开始的预算（`docs/constraints.md` 里的资源上限）时，才先问用户（`rl request --kind approval`，答复用 `--approve|--change`，见 5.2）。协调者按 `rl status` 里的已用量和新假设的预计用量（`cost`）判断。
- 记下以后又要改：还没检验的假设用 `rl hypothesis revise` 改命题和范围，不要的假设用停止决定撤下。
- 用户后来拿来新文档、要换方向时，办法相同：`rl tree prompt --from <新文档>`。说明里带着现有的树，草稿里的新假设可以挂到已有的假设下面。
- 宿主不能开子代理时（第 13 章），协调者自己照 `rl tree prompt` 写草稿。文档会进它的上下文，只此一次。
- 原来拆树交付时的检查一并去掉：计划覆盖检查（`tasks._plan_coverage`）、`left-out.md`、`prep.yaml`。`--source` 改成可选，只说明假设出自哪份文档的哪一节（7.3 的启动包靠它找到文档）。
- 不再提供 `--composite`。任何假设都可以直接有假设任务，裁决引用证据即可，不再要求引用子假设的决定（`research.finalize`）。旧记录里的复合假设照读，第 4 章里“子假设都已收尾”的提示对它们照旧。

### 7.3 假设任务

假设任务是一个科学家检验一个假设的全部工作，下面可以有很多任务：

1. 先定怎么检验：做哪些工作，先后顺序，判定规则。文档里已经写明的判定规则直接用。启动包给出来源文档的路径和假设的 `source`，文档按需去读，启动包里不放全文。
2. 开任务。工程开准备任务，派给研究者写；实验开执行任务，流程照旧（清单、受保护范围、语义测试、派发）。可以同时开很多个，先后关系用 `--depends-on` 写明，研究者并行做。
3. 开发阶段的结果改变了方案时，由这位科学家自己调整。改动涉及用户定下的东西（判定规则、范围、预算等约束）的，照旧请用户决定（`rl request`）。
4. 一个假设一个科学家。需要别人判断的，找顾问（`rl advise ask`），不为此拆出假设。
5. 最后写裁决，交付。

检验计划交给科学家自己决定（11-27 用户定）。用户先提议在假设上挂一份有版本的计划（写在本文初稿的 7.4 节，提交 `461b8b2`，后来删去），后来说：“还是多余了, 交给科学家自己决定吧”。所以插件不另设计划记录，也不检查有没有计划；也不再要求每个实验都由一条路线决定引出，`rl experiment add --motivated-by` 改成可选。

科学家卡只留假设任务这一段，写明：检验要做的工作是这个任务下面的任务，不是新假设；结果引出了新问题，才提新假设（候选）。

协调者卡写明：建树之后，通常只放行一个假设任务。要并行，靠这个任务下面的工作，不靠拆出更多假设。

  - **交付和并发的取消**：交付记下开始时读到的任务修订号，写入时再核对一次。检查期间任务被取消、接手或退回时拒绝交付，什么也不写。
  - **运行登记**：重试（`--run`）的类别跟原运行，不看这次给的 `--trial`，未提交改动的检查也照原类别做。每个 `--commit` 都要在仓库里解析成提交，完整的 40 位也一样。本机运行（不带 `--resource`）跑的是工作树，所以即使写了 `--commit`，也照样检查未提交的改动；走执行器的运行检出的就是写的那个提交，不查。
  - **本地验收中断**：本地验收开始时记下 `merge_proc`。再跑 `rl task accept` 时，如果那个进程已经不在（或者没有进程信息，且开始已超过 30 分钟），就从头重新验收。如果进程还在，只报告它在跑。开始已超过 30 分钟（本地测试的超时）时，不管那个进程号还在不在，都按中断处理，因为进程号会被重用。只有配置成作业测试的验收，才等合并测试作业。
  - **`--force`**：只在这次交付的合并测试已经失败后生效。作业模式下第一次就带 `--force`，先照常跑测试作业，并说明原因；作业失败后，再带 `--force --reason` 才移动主线，标记里写明是哪个作业失败。合并测试失败的公共准备任务不退回研究者，留在“已交付”等协调者，由协调者 `--force` 或退回。合并冲突照旧退回研究者。测试失败时，命令通知协调者，待办也列在协调者那里。测试在本地跑还是作为作业跑都一样；有科学家帮它回答过阻塞时，也照样通知协调者（`tasks.decider`）。交付时完成检查就没通过的，交给接收交付的一方：协调者，或者协调者用 `rl task release --to scientist` 交给的那个科学家（第三轮复查）。

## 附录 A. 拒绝的归类（实现时整理）

逐条过了 `tasks.py`、`runs.py`、`reviews.py`、`research.py`、`messages.py`、`tree.py`、`documents.py` 里的拒绝（`store.py`、`util.py` 等是读写和格式的底层检查，都属于“记不下来”）。括号里是函数或行为。

**记不下来**

- 编号不存在或类型不对：`tx.require` 的全部调用；派发准备和执行以外的任务；`set_prep` 用在非准备任务上；阶段只收假设任务和公共准备任务；审核目标的类型（`reviews.request`，`--recheck-of` 指向的轮次种类或目标不同）；运行属于执行或准备任务，`--run` 属于别的任务；证据引用的不是结果或 attempt；决定的目标类型；`--close` 不是问题；讨论挂在顾问单上；更正指向别的 attempt。
- 定义记录的参数缺失或格式错：假设任务卡的四项；执行任务的实验；准备任务的要求和完成检查；交付的结论和局限；`--force` 没有 `--reason`；`rl request` 没有 `--task`；`--by` 不是 coordinator 或 user；批准没有 `--approve|--change`；`rl task test --record/--attempt`；`--purpose`；证据运行的 `--arm`；观测、执行引用、产物、用量的字段；审核答复的 `--verdict`、`--findings`、`--close`；`rl review reject` 没有理由；假设的 `--purpose`；存疑的 `--lack` 和结论；实验的 `--hypotheses`；证据的来源；决定的种类、目标、状态、`--did/--means`；关系名；草稿的问题（`rl tree check` 列出的那些）；审核答复没有 `--at`。
- 要封存或解析的文件不存在或解析不了：计划；文档；提交里没有实验清单；`--commit` 不是提交；没有测试命令；执行任务没有工作树可封存；产出没有提交到任务分支；结果清单的状态不是 partial 或 complete；没有草稿；`rl doc commit` 的文件不存在；封存对象缺失或摘要不符。
- 并发：测试期间设计或测试命令变了；验收时任务刚被改动（两处）；交付时任务在完成检查期间被取消、接手或退回；登记时验收或持有者、实验修订变了（两处）。
- 记录的状态做不了这一步：认领已交付或已结束的任务（交付后由 `rl task return` 退回）；放行不在排队的任务；取消已结束的任务；派发、阻塞、交付不在进行中的任务；回答没有阻塞的任务；验收、退回没有交付的任务；转发或答复已答复的请求；没有等待答复的审核；已答复的顾问单；发现已经是那个状态；没有存疑可定、已有结论可推迟的假设；对已结束任务开审核（它的轮次随任务结束，新开的一轮一开就结束）。
- 问题发给用户或自己：用户不是会话，改用 `rl request`。

**会是假的**

- 改写已记下的事实：已封存的实验换了清单（要新修订）；封存后改实验要 `--reason`，记成新修订；已有结论的假设改命题；项目换计划（新方向用 `rl tree prompt --from`）；已结束的记录的文档加修订；任务换阶段；测试结果已记下；观测和执行引用与已记的冲突；计费引用已记下；同一运行换了规格。
- 记下的和实际不符：工作树有未提交的改动时记测试结果；证据运行和准备运行登记时工作树有未提交的改动（试跑不查；重试按原运行的类别查；本机运行写了 `--commit` 也查）；`--commit` 在仓库里解析不成提交；没有等它的验收、或不是合并提交的合并测试；任务分支在交付之后又有提交，验收的不是交付的；结果清单属于别的 attempt 或别的运行；审核答复的 `--at` 不是这一次的目标（同一提交上改过设计时，要带设计标识）；裁决写的是另一个命题；`rl doc commit` 只提交 `docs/glossary.md` 和 `docs/explanations/*.md`（代码进主线要经过任务和验收，否则记成文档提交的其实是代码）。
