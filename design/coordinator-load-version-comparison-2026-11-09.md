# 协调者负载的版本对比：`73d0124` 与当前版本

日期 2026-11-09。配套文档是[协调者上下文负载：问题分析与新设计建议](coordinator-load-analysis-and-redesign-2026-11-09.md)，下文称设计文档。数字来自 bypass-lora 的运行日志和账本。第 8 章是建议，尚未实现。

## 1. 核心内容总结

这份报告回答两个问题：`73d0124` 上是否没有设计文档列出的问题，当前版本又是怎样引入它们的。比较对象是 bypass-lora 同一项目的两段运行。

大部分问题在 `73d0124` 上已经存在。11-01 至 11-03 插件停在该提交，协调者（Claude Code，Opus 5.5）57 小时用了 9.48 亿输入 token 和 560 个 turn。11-07 至 11-08 的当前版本协调者（Codex，gpt-6-astra）32.6 小时用了 4.16 亿和 122 个 turn。平均每个进入协调者的事件消耗 104 万和 114 万输入，基本持平。协调者占全项目 token 的比例从约 40% 降到约 29%。

当前版本新增的问题都来自研究说明页。写命令同步重渲染页面，`LOCKED` 从 4 次增加到 57 次；页面和说明文件的工作进入协调者主线程，相关工具调用从 4.0% 升到 26.9%。

复盘只统计 Codex 日志，旧协调者不在其中，所以协调者的消耗看起来像是 11-07 才出现。

## 2. 比较对象和方法

两段运行下文称旧期和新期。

| | 旧期 | 新期 |
|---|---|---|
| 时间（UTC） | 11-01 02:16 至 11-03 11:14 | 11-07 05:41 至 11-08 14:16 |
| 插件版本 | `73d0124` | `a8a70a9` |
| 协调者 | Claude Code，Opus 5.5，会话 `d2bf5e61` | Codex，gpt-6-astra（xhigh、max），会话 `01a1b483` |
| researcher | 以 Codex（gpt-6-astra、gpt-6.1-sol）为主，researcher-3 和后期的 researcher-2 用 Claude Opus 5.5 | Claude Sonnet 5.5 |
| reviewer | Codex 和 Claude Opus 5.5 | 以 Codex gpt-6.1-sol 为主，11-08 起有 Claude Opus 5.5 |

版本依据：`73d0124` 提交于 11-01 01:38 UTC，项目在 02:19 UTC 初始化，下一批插件提交从 11-05 才开始。旧协调者调用的 rl 来自 Miyabi 检出目录的 `dist/claude/plugins/smooth-research/bin/rl`，reflog 显示该目录的后续提交从 11-05 晚上开始。新期开始前，该目录在 11-07 12:30 JST pull 到 `a8a70a9`，账本在 11-07T03:46Z 记录了 schema 2 到 4 的升级，build `6eac92ed6bd2ae20-9f8fce44`。

数据来源：

- Claude Code 会话日志：Miyabi 上 bypass-lora 相关的 40 个文件（含 subagent），按 `message.id` 去重。输入等于 `input_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens` 之和。
- Codex 会话日志：`docs/bug-report/codex-token-retrospective-2026-11-08.md`（下文称复盘）的审计 JSON，共 70 个会话，以及协调者会话的逐行统计。输入取 `input_tokens`，已包含缓存。
- 账本快照：`research/snapshots/restart-method-preparation-20261108`，截至 11-07T18:21Z。
- 两个版本的源码和 git 历史。Miyabi 上只做了只读统计。

计数口径：

- turn：旧期是协调者回合结束（`end_turn`）后收到的第一条消息开启的回合。新期取 `task_started`，共 122 个，复盘按另一种方式记为 116。
- 事件：进入协调者上下文的 rl 通知、后台任务结束提醒、作业通知和用户消息，包括回合中途排队进入的。旧期约 915 条，其中 rl 通知 568 条，账本同期发给协调者的消息是 576 条，后台任务结束提醒 293 条。新期约 366 条，其中 rl 消息 287 条，`[miyabi-mcp]` 作业通知 63 条。

消息平均长度的新期值只覆盖账本快照内的 11-07。

协调者的输入量可以按设计文档第 3 章的方式拆开：

```
旧期  560 turn × 7.27 请求/turn × 23.3 万输入/请求 ≈ 9.48 亿
新期  122 turn × 21.0 请求/turn × 16.3 万输入/请求 ≈ 4.16 亿
```

新期的 turn 少 78%，单个 turn 的请求数是旧期的 2.9 倍。这个倍数由两部分相乘得到：每个 turn 处理的事件从 1.6 个增加到 3.0 个（Codex 协调者的 122 个 turn 里有 72 个处理了两条以上消息），每个事件的请求数从 4.4 增加到 7.0。第一部分把同样的事件放进更少的回合，总量不变。第二部分让单个事件变贵，其中约六成和 6.2 节的页面工作有关。

按开启 turn 的原因拆分：

| 原因 | 旧期 turn | 旧期输入 | 新期 turn | 新期输入 |
|---|---:|---:|---:|---:|
| rl 消息通知 | 343 | 6.11 亿（64%） | 86 | 2.93 亿（70%） |
| 作业结束或后台任务结束 | 183 | 2.31 亿（24%） | 27 | 1.09 亿（26%） |
| 用户消息 | 30 | 0.72 亿（8%） | 7 | 0.17 亿（4%） |

旧期第二行主要是协调者启动的后台任务结束时的提醒（后台 `notify listen` 启动过 123 次），新期是 `[miyabi-mcp]` 通知直接打进窗格。旧期被唤醒得更频繁，每次做的事更少：343 个通知 turn 的工具调用中位数是 2，其中 119 个（35%）只调用了 0 到 1 个工具。

通知内容按关键词近似分类。旧期账本里，作业相关的 NOTE 占发给协调者字符的 60%，RESULT 13%，`needs a reviewer` 9%。新期（到 11-07T18:21Z）RESULT 32%，作业相关 NOTE 26%，preflight 和 GO 18%，`needs a reviewer` 10%。

## 6. 当前版本新增的两个问题

### 6.1 写命令同步重渲染页面

`5b46727`（11-05）加入 `docs/research.html` 和 `_refresh_page`，`c943c58` 加入 `labels.resolve`。`73d0124` 的 `cli.py` 没有这一步。设计来自 11-05 的定稿文档：决定 12 写明改记录的命令结束时自动重渲染，理由是页面始终和记录一致，没有采纳只在阶段结束时渲染。需求的起点是用户 11-02 要求状态更新后同步页面，11-03 指出报告不可读。

| `LOCKED` 错误次数（工具结果） | 旧期 | 新期 |
|---|---:|---:|
| Claude 会话 | 2 | 34 |
| Codex 会话 | 2 | 23 |
| 合计 | 4 | 57 |

新期的 57 次里，协调者 18 次，researcher 32 次，其他会话 7 次。bypass-lora 的报告实测 `rl view` 约 2 分 43 秒，`decide` 写入后的刷新又占 1 分钟，中断时的 traceback 落在 `_refresh_page`、`_words` 和 `labels.resolve`。两段运行的并发会话数和账本规模不同，也没有做锁级追踪，这些 `LOCKED` 不能全部归给页面刷新。

### 6.2 页面和说明文件进入协调者主线程

`5b46727` 和 `fd63183` 把说明页的维护写进了协调者的流程：`SKILL.md` 要求阶段结束时运行 `rl view --todo`，写或修订它列出的说明，再运行 `rl view`。

下表用工具调用里的命令和路径匹配页面相关工作。新期匹配 `rl view`、`research/notes/explanation*` 和 `docs/research.html`，旧期匹配 `rl view`、`docs/explanations/`、`hypothesis-tree` 和 `research-graph`。

| | 旧期 | 新期 |
|---|---:|---:|
| 页面相关的工具调用 | 155 / 3,848（4.0%） | 597 / 2,216（26.9%） |
| 发出这些调用的请求的输入 | 3,600 万（3.8%） | 9,380 万（约 22%） |

新期的 597 次里，358 次涉及说明文件，258 次涉及 `docs/research.html`，其中 213 次同时挪动或复制 HTML，这是项目为绕开自动刷新写的包装命令，另有 50 次运行 `rl view`。这几类有重叠。

扣掉这些请求后，新期每个事件约 5.4 个请求，旧期是 4.4，按这个估算，每事件请求数的增长约六成和页面工作有关。这些调用里有的同时在做别的事，六成是上限。设计文档没有写这一项。

## 7. 其他变化

这些变化出现在新期，和插件版本没有直接关系，或者原因没有拆开。

协调者换到 Codex。新期协调者的 compaction 比旧期频繁，重读技能文档的 turn 占 47%，57 个里有 47 个发生在 compaction 的同一 turn 或下一 turn。旧协调者只有 10 个这样的 turn，其中 2 个紧跟 compaction。两版都要求协调者按 `SKILL.md` 工作。

研究者自己等短作业的比例下降。Claude 上的 researcher 旧期提交 233 次作业、调用 `job_wait` 196 次，每次提交 0.84 次；新期提交 159 次、调用 47 次，每次提交 0.30 次。两版 `workflow.md` 对短作业的写法相同（"Use a bounded wait for short jobs when supported"）。`433a50b` 在 researcher 工作包第 4 步加了把通知发给协调者的说明，只针对长作业，这是否影响了 researcher 的选择没有核实。

消息变长。账本里发给协调者的消息，NOTE 的中位长度从 503 升到 1,125 字符，RESULT 从 974 升到 1,340，WAIT 从 126 升到 260（均值从 163 升到 1,256）。消息由 researcher 撰写，这段时间 researcher 换成了 Sonnet 5.5，插件的 600 字符通知上限两版相同。`433a50b` 要求 WAIT 的 `--summary` 写明通知及其目标，只能解释 WAIT 的一部分增长。

逐批 GO。插件文档、`docs/constraints.md`、项目 `AGENTS.md` 和 11-05 计划里都搜不到这个词，最早见于 11-07 协调者和 researcher 的往来。

工具输出变多。每次请求带回的工具输出增加到 3.8 倍，主要来自协调者手工核对时的 shell 命令（第 5 章 4.5 行）。`rl inbox` 和 `rl show` 的份额两期接近，分别是 13% 和 12%。

旧版本看起来没有这些问题，可能的原因在统计范围。11-08 的复盘只读 Codex 日志。旧期协调者在 Claude Code 上，不在这批日志里，旧期 Codex 的用量全是 researcher、reviewer 和 advisor。新期协调者换到 Codex 后第一次进入审计，显示为 4.18 亿。用户在 11-03 列出的问题只有报告可读性和 Codex 容量报错后无人继续两条，协调者负载当时没有被单独统计。

## 8. 对重新设计的影响

设计文档第 5 章的建议继续成立。两段运行里每个事件的平均输入都在 100 万左右，减少进入协调者的事件仍是主要手段，这一点在 `73d0124` 上同样成立。需要调整的有四处：

1. 5.9（页面刷新移出写路径）应该提前。它是这次比较里确认的回退，不依赖其他改动，也能去掉项目挪动 HTML 的包装命令。
2. 增加一项：说明文件的写作移出协调者主线程，交给 researcher 或子代理，`rl view --todo` 放在阶段边界。11-05 的定稿设计已经允许子代理写说明，目前 `SKILL.md` 的流程默认由协调者完成。
3. 增加一项：降低 Codex 协调者在 compaction 后重读文档的成本，例如提供一份短的规则卡。设计文档 5.7 里"例行动作的命令直接写在输出里"可以覆盖一部分。
4. 5.10 的用量报告需要同时读 Claude 和 Codex 的日志，只读一家时看不到跨 host 的角色分布。

## 9. 限制和未核实事项

- 两段运行不是对照实验。协调者的 host 和模型、researcher 的模型、研究阶段、项目规则和并发会话数都不同，分离不出插件版本单独的作用。
- 两家的 token 计数和缓存统计方式不同，订阅额度的扣法不在日志里，所以无法判断哪一段更费额度。
- 两段的任务大小不一样，平均每任务的数字只作量级参考。
- 账本快照截至 11-07T18:21Z，新期的消息分类和长度只覆盖这个时点之前。
- turn 和事件的计数依赖日志格式，Claude 和 Codex 的定义略有差别，见第 2 章。
- 页面相关调用靠命令和路径匹配，有的调用同时在做别的事。
- GO 只搜索了字面词，中文的"放行"类措辞没有统计。
- 重读文档和 compaction 的关系是时间上的相邻，机制没有单独验证。
