## 1. 总的看法

设计要解决的问题很明确：协调者被消息淹没。它用了三个主要办法：

- 按假设把工作整块交给科学家，协调者每个假设只收一条结论。
- 科学家直接写实验代码和判定函数，不再先写成文字合同，再让研究者翻译回代码。
- 通知不存成消息，每个角色的待办从记录状态查出来。通知丢了，会话重启了，该做的事都还在待办里。

这三条互相配合，方向是对的。下面的意见都不改这条主线，补的是它还没有覆盖的地方，一共四类：

1. 有些事现在由协调者顺手在做。设计把协调者的职责收窄以后，这些事没有交给别人。最要紧的是代码合并。
2. 有些判断交给了按设计看不到相关情况的角色。例如，科学上的争议升级给不读代码的协调者。
3. 有些检查靠模型自觉，或者靠审核者标一下，其实 CLI 可以直接查。最要紧的是运行配置。
4. 成本和节奏上有几处可以更省：科学家被唤醒的方式、小实验的流程、第一次试运行的时间。

## 2. 意见一览

轻重的含义：

- 高：不补上，实现会卡住，或者实验结论可能出错。
- 中：会多花钱或留下隐患，可以在实现对应部分时一起定。
- 低：顺手可改。

| # | 问题 | 建议 | 轻重 |
|---|---|---|---|
| 1 | 任务验收后，没有人把代码合并回主线 | 验收时由 CLI 合并；有冲突记成待办，交给验收它的科学家 | 高 |
| 2 | 分支和工作目录说是跟着任务走，现有实现是跟着会话走 | 工作树按任务建，交接时研究者直接在里面启动 | 高 |
| 3 | 没有 herdr 时新流程怎么运行，没有交代 | 现在二选一：只支持 herdr，或者定义不靠常驻会话的跑法 | 高 |
| 4 | 监视现在报给协调者的事，设计里只留下了“失联” | 逐类写明去向：换模型交给监视，对话框加一种固定类型 | 高 |
| 5 | 准备任务只有几句话，公共的准备工作没有主人 | 研究者写代码；公共准备挂在项目下；启动包列出可复用的产物 | 高 |
| 6 | 科学争议升级给协调者，它没有材料可判 | 方法和结论的升级交给顾问裁决，协调者只知道结果 | 中 |

| 8 | 排期的依据不在数据库里，“阶段”没有定义 | 假设任务可以提前排队；阶段记成一条记录 | 中 |
| 9 | 假设树一开始拆得对不对，没有人把关 | 假设树和第一阶段的排期先给用户看 | 中 |
| 10 | 科学家遇到无权决定的事，只有预算申请一个出口 | 预算申请扩成决定请求 | 低 |
| 11 | 最容易出错的运行配置，在保护范围的边上 | 设计提交带一份机器可读的实验清单，登记运行时核对 | 高 |
| 12 | “方法还是工程”只靠审核者标一下 | 定位落在受保护范围内的发现默认算方法类；按符号保护 | 中 |
| 13 | “第一次运行前封存”没说清是哪一刻；冒烟会被审核卡住 | 交接时封存；运行分成试跑和证据运行 | 高 |
| 14 | 作业结束不是数据库里的状态变化，这类待办会丢 | 记下预计结束时间，过时没有记录就进待办 | 中 |
| 15 | 一条记录可能同时等两个人；异常只有“失联”一种 | 待办做成规则表；每项待办记“等了多久”，超时逐级上报 | 中 |
| 16 | 科学家每醒一次都要重读整段对话 | 按规则选择续用还是重开；试运行时强制重启一次 | 中 |
| 17 | 小实验也走全套流程 | 定一条由 CLI 判断的快速通道 | 中 |
| 18 | 预算不拦可以，但超了没人知道 | 到线提醒，不拒绝；显示还在排队的用量 | 中 |
| 19 | 八个阶段做完才第一次试运行 | 先手工试一个假设；先做旧流程里也有用的部分 | 高 |

## 3. 设计没写到、但总得有人做的事

### 意见 1：代码合并没有人负责

- 设计怎么说：协调者不持有任务，没有工作目录，不读代码（7.4）。任务由科学家验收（6.1）。全文没有提到任务分支验收以后怎么并回主线。
- 现在怎么做：协调者验收任务后，自己把任务分支合并进主线。`rl task accept` 会提示要合并哪个分支，研究者的工作说明里也写着“不要自己合并，协调者验收后合并”。
- 问题：照新设计，这一步没有人做，后果有两个。
  1. 同一个假设的第二个实验想接着第一个实验的代码写，可主线上没有那些代码。
  2. 几个科学家同时工作时，都会改到共用的核心文件。设计自己的范例里，E-0035 的受保护路径就有 `src/train.py` 这种公共训练代码。各改各的分支，没有人对齐，后面的实验就建立在互不相同的“方法核心”上。
- 建议：
  1. 把验收和合并绑在一起。科学家验收任务时，CLI 把任务分支合并进主线，保留合并提交，这样已登记的运行引用的提交仍然找得到。
  2. 合并有冲突时不自动处理。把它记成这个任务上的一个状态，进验收它的科学家的待办，由科学家开一个小任务让研究者解决。合并后主线上的语义测试不通过，也这样处理。协调者不参与。
  3. 写明新任务的分支从当时的主线开始。依赖关系（`DEPENDS_ON`）已经要求前置任务先验收，验收就是合并，所以后面的任务自然拿得到前面的代码。
  4. 主线上的受保护文件被别的任务改了以后，正在进行的任务不受影响，因为它们的运行钉在自己的提交上。但核验行要加一行，说明主线上的方法核心比本任务的设计提交新，由科学家决定要不要跟进。

### 意见 2：分支和工作目录说是跟着任务走，现有实现是跟着会话走

- 设计怎么说：任务的分支和工作目录 `research/work/T-xxxx/` 从科学家建任务时开始，交接时一起转给研究者（6.1）。
- 现在怎么做：每个研究者会话有自己的 git 工作树，路径是 `<项目>-worktrees/<会话名>`，分支名里也带会话名。
- 问题：
  1. git 不允许同一个分支同时在两个工作树里检出。科学家写完代码以后，如果它的工作树还停在任务分支上，研究者的工作树就检不出这个分支。
  2. 科学家没提交的文件留在它自己的工作树里，研究者看不到。
  3. 科学家要同时持有两三个任务（4.2）。只有一个工作树的话要来回切分支，现有代码在有未提交改动时会拒绝切换。
  4. `research/work/T-xxxx/` 到底在哪个检出里，设计没有说。它可以在任务的工作树里，跟着分支走；也可以在主项目目录里，各会话用绝对路径访问。两种理解都说得通，做法却不一样。
- 建议：工作树按任务建，不按会话建，例如 `<项目>-worktrees/T-0042`。交接时研究者的会话直接在这个目录里启动，分支、未提交的文件和工作目录都原样在那里。科学家同时做几个任务，就有几个任务目录。`research/work/T-xxxx/` 放在任务的工作树里，要留的文件在交付时登记成产出。运行产生的大文件仍然放主项目的 `research/artifacts/` 下，和现在一样，这样任务合并后删掉工作树不会丢东西。

### 意见 3：没有 herdr 时新流程怎么运行，没有交代

- 设计怎么说：科学家交出任务后结束本轮，有消息时被唤醒（4.2）。科学家启动审核者和研究者（第 2 章）。CLI 给活会话发一行提醒（8.8）。这些都要求会话一直开着，能被别的进程叫醒。这是在 herdr（给编码 agent 用的终端复用器）里的运行方式，但全文没有出现 herdr。
- 现在怎么做：没有 herdr 时，插件用无头方式运行（`rl delegate`、`rl review run`、`rl advise run`），Claude Code 里还可以用原生子代理 `researcher`。11-09 文档 5.1 第 5 条写过“没有 herdr 的运行方式继续可用”，但 5.1 整节已经被设计取代，这一条有没有保留不清楚。
- 问题：无头方式下没有“叫醒”这回事。启动方要么等对方做完才返回，要么把对方放到后台，自己回头轮询。科学家做不到“交出去，不等结果，有消息再醒”。原生子代理能不能再启动审核者和研究者这样的两层嵌套，也需要先核实。实现到第 5 阶段（会话）时一定会碰到这个问题。
- 建议：现在就二选一，写进设计。
  - 选项 A：新流程只在 herdr 下可用。没有 herdr 时保留旧流程，CLI 给出明确提示。做起来简单，代价是两套流程长期并存。
  - 选项 B：给新流程定义一种不靠常驻会话的跑法。每个会话手头没事就结束。监视进程发现某个角色的待办里有事，又没有活会话，就按启动包新开一个。这种跑法不需要 herdr。
  
  我倾向 B。设计本来就要求任何会话都能从数据库重新开始（4.5、第 11 章），B 只是把这条恢复路径当成常规路径来用，和意见 16 是同一个机制。

### 意见 4：监视现在报给协调者的事，设计里只留下了“失联”

- 设计怎么说：监视只在“会话断开且无法恢复”时发失联，发给建任务的一方（第 3 章、8.2）。协调者只收七种固定类型（7.3）。
- 现在怎么做：监视每 5 分钟看一遍所有会话，下面这些情况都报给协调者，由协调者处理：
  - 会话停在权限对话框上；
  - 一轮对话出错，重试无效；
  - 长时间没有进展；
  - 订阅额度快用完，需要换模型。
  
  其中回答对话框（`rl agent answer`）和换模型（`rl agent switch`）两个命令只允许协调者执行。会话的工作说明里也写着：有问题或要申请权限时去问协调者，不要问用户。
- 问题：这些情况在设计里没有去处。它们不在协调者的七种固定类型里，按 9.1 会被拒绝发送。可如果没有人回答对话框，那个会话就一直停着，它的任务也跟着停，却不算“失联”。额度问题对科学家更明显：它用最强的模型，额度最紧。
- 建议：逐类写明去向，能交给规则的就不交给模型。
  - 换模型：监视自己做。会话空闲、额度低时，关掉旧会话，用同角色的下一个模型按启动包新开。新会话从数据库恢复，所以不需要旧会话先写交接文档。
  - 重启和重试：监视已经在做，保持不变。
  - 权限对话框和其他需要判断的情况：加一种固定类型“会话需要决定”，发给协调者。协调者现在上下文很小，手里有目标和约束，适合判断；判断不了再问用户。
  - 顺便分开两个名字。现有命令 `rl task handoff` 的意思是“同一个角色换一个会话接着做”，要带交接文档。设计把“交接”用来指“科学家把任务交给研究者”。两件事都还需要，建议用两个词，比如“交办”和“换人”，免得实现和文档互相误读。

### 意见 5：准备任务只有几句话，公共的准备工作没有主人

- 设计怎么说：准备工作是任务，不建实验（10.2 第 1 条）。准备任务指向它服务的假设，由科学家验收（第 8、9 条）。产出通过依赖关系进入用到它的实验（第 4 条）。执行任务的流程写了两章，准备任务只有这几句。
- 问题：有四件事没说。
  1. 谁写代码。数据管线、工具验证、计时这类工作是工程活。按第 1 章第 6 条原则，科学家不该把 token 花在这上面，但设计里只有“科学家写代码、研究者修工程问题”一种分工。
  2. 要不要审核，凭什么验收。准备任务没有实验，也就没有设计提交、判定函数和语义测试，现有的交接条件和核验行都套不上。
  3. 公共的准备工作归谁。训练框架、数据管线、公共基线服务很多假设。可协调者只建假设任务，其余任务都挂在某个科学家的假设任务下面（10.1）。结果是谁先用到谁来建，花费记在它的假设上，别的科学家不知道已经有了。
  4. 已有的东西怎么复用。消息设计页的第 7 个范例里，协调者要靠提问才知道 E-0035 的 Base 结果能不能给 H-0016 用。两个并行的科学家各自重训一遍同样的基线，是很容易发生的浪费。
- 建议：
  1. 准备任务由研究者写代码。科学家只写一小段要求：要什么产出，怎么算合格。合格标准最好是一条可以运行的检查命令。
  2. 验收看这条检查通不通过。产出里有后面实验要用的核心代码时，才需要审核。
  3. 项目开始拆假设树的那个短会话，同时列出公共的准备任务。它们挂在项目下面，不挂在某个假设下面，花费单独记。验收仍然看检查命令，由第一个依赖它的科学家确认。
  4. 启动包加一小节“已有的可复用产物”，每个一行：公共基线、数据版本、已验收的准备任务产出。科学家动手前先看有没有现成的。
  5. 给准备任务一个固定用途：在新的代码区域写第一个实验之前，先让研究者摸清真实环境，交一份事实清单，包括模型的模块名、张量形状、单批显存和单步耗时。科学家只在 CPU 上跑玩具测试（5.5）。它对真实环境的假定如果错了，要到研究者运行时才发现，那时只能走设计阻塞，把最贵的模型叫回来返工。

## 4. 有些判断交给了看不到情况的角色

### 意见 6：科学争议升级给协调者，它没有材料可判

- 设计怎么说：两次审核后仍有 medium 以上的发现时，科学家段和结论审核的升级发给协调者，由它“决定未关闭的发现怎么处理”（8.2、8.7）。这一项在第 14 章第 4 项里还是待确认。
- 问题：协调者的启动包明确不含代码、diff 和审核讨论（第 11 章），它的职责是排期和给预算。升级上来的却是全系统里最需要专业判断的问题，例如“这个结果该判挑战还是不确定”。协调者要么照着其中一方的说法批准，要么为了判断把它本不该看的材料全读一遍，回到老问题上。
- 建议：涉及方法和结论的升级交给独立的第三方。CLI 把这一回合里双方的说法和引用的证据打成一个包，开一张顾问单。顾问给出裁决意见，科学家照此修改，或者写明不采纳的理由。争议涉及用户约束（目标、可以声明的范围）时，再由协调者转给用户。协调者只需要知道结果，因为它影响排期。研究者段的工程类升级仍然发给科学家，不变。

### 意见 7：一个假设的结论影响别的假设时，没有人会发现

- 设计怎么说：科学家只看本假设和祖先的决定（第 11 章）。协调者看到的是每个假设一行，加上假设结论的核验行（9.3）。
- 问题：假设之间有前提关系。消息设计页的范例 1 里写着“H-0014 是 H-0016、H-0017 的前提”，但这只是说明里的一句话，不是数据库里的关系。设想科学家 A 把 H-0014 判为被挑战，另一个科学家正在跑以它为前提的 H-0016。后者不知道，继续花计算。协调者收到 A 的结论，核验行里只有建议的子假设，看不出它影响了谁。旧流程里协调者什么都看，所以能发现这种情况，代价是被淹没。新流程里要到阶段结论才有人把各个假设放在一起看。
- 建议：
  1. 把“前提”记成假设之间的一种边。可以用现有的非主父 `DERIVED_FROM`，或者加一种边。
  2. 一条决定改了假设状态时，CLI 顺着这些边找出受影响、还没有判定的假设，在它们的科学家待办里加一项，例如“上游结论变了：H-0014 被挑战（D-0102）”。继续、改设计还是停，由那位科学家决定。现有的 `needs_recheck` 是同一个思路：结果被否定时，给依赖它的证据和决定打上标记。这里只是沿假设之间的边再走一步。
  3. 假设结论的核验行加一行 `affects`，列出受影响的假设和它们的状态，协调者排期时能看到。

### 意见 8：排期的依据不在数据库里，“阶段”没有定义

- 设计怎么说：协调者决定先做哪个假设、给多少预算（7.1）。它的启动包是目标和约束一屏，加上假设任务每个一行（第 11 章）。阶段结束时写阶段结论和阶段报告（第 2 章第 11 步）。
- 问题：
  1. 假设任务是排到了才建的。还没排到的候选假设、为什么是这个顺序、剩下的预算打算怎么分，这些只存在协调者的对话里。协调者压缩或重启后，启动包里没有它们，这和“从数据库恢复”的原则（第 1 章第 4 条）不一致。决定只能由科学家写（10.1），协调者自己的判断没有地方记。
  2. 没排上的候选假设会一直停在 `candidate`。停掉一条路线要开科学家会话，还要结论审核，所以它们实际上会被默默放着，假设树越来越难读。
  3. “阶段”什么时候结束没有定义。阶段报告是用户唯一的例行检查点，触发条件却只靠协调者自己判断。
- 建议：
  1. 假设任务可以提前建，状态是“排队”，带优先级和一句理由。排期表就成了一次查询，协调者重启后看得到，用户也能随时看到接下来要做什么。
  2. 协调者可以给候选假设标“暂不做”，写一句理由。这只改排期，不改假设的判定状态，所以不需要结论审核。
  3. 把阶段记成一条记录：它包含哪些假设任务，或者一笔预算。里面的假设任务都验收了，或者预算用到了，CLI 就通知协调者“阶段结束”，和“子假设已全部判定”的做法一样。

### 意见 9：假设树一开始拆得对不对，没有人把关

- 设计怎么说：项目开始或换方向时，协调者开一个短的科学家会话，把计划拆成假设树（4.4）。之后协调者按这棵树排期。
- 问题：后面所有的计算都花在这棵树上，它却是全流程里唯一没有独立检查的产出。改一个假设的状态要结论审核，建一整棵树不需要任何人看。用户要到第一份阶段报告才看到它。
- 建议：把“假设树加第一阶段的排期”作为给用户的第一份报告，用户批准或修改后再开始花计算。它很短，设计自己算过，44 个假设每个一行不到 5 KB。换方向时同样处理。如果想在给用户之前先筛一遍，可以让审核者只回答一个问题：每个假设是不是可以检验的命题，有没有漏掉明显的竞争解释。

### 意见 10：科学家遇到无权决定的事，只有预算申请一个出口

- 设计怎么说：科学家发给协调者的固定类型只有假设结论、预算申请、阶段结论和答复（7.3、8.3）。
- 问题：超出科学家权限的事不只有预算。例如，检验这个假设需要用约束文档不允许的数据，或者假设的表述要改到超出计划的范围。这类事要协调者甚至用户决定，却没有对应的类型。科学家要么把它塞进预算申请，要么自己做主，要么提前交一个假设结论把会话结束掉。
- 建议：把“预算申请”扩成“决定请求”，内容是卡在哪、有哪些选项、建议哪个、各自的代价。预算是其中一种。协调者能定的自己定，不能定的转给用户。协调者发给用户的决定请求已经是这个格式（8.1 最后一行），这里只是补上科学家到协调者这一段。

## 5. 能让 CLI 查的，不要靠模型自觉

### 意见 11：最容易出错的运行配置，在保护范围的边上

- 设计怎么说：受保护路径包括方法核心、实验定义（各臂、对照、精度、数据划分）、分析和判定代码（5.1）。受保护路径以外，研究者按需要改；工作流页的图 5 把“作业脚本、配置”列在这一层。实验的定义以设计提交里的代码为准，不再写长合同（5.1）。
- 现在怎么做：合同文件开头可以有一段机器可读的 `arms:` 清单，`rl run register` 只接受清单里的臂。
- 问题：
  1. 设计自己举的方法错误是“对照组用错学习率”（5.2）。这种错通常不出在受保护的代码里，而出在实际运行时传进去的配置上：作业脚本里一个命令行参数，就能盖掉代码里的默认值。研究者改作业脚本不碰任何受保护路径，语义测试也照样通过。
  2. 现有的检查帮不上忙。导入结果时，CLI 比的是结果清单和登记的运行规格是否一致，而运行规格是研究者自己填的。研究者从登记到运行一路用同一个错的学习率，所有检查都会通过。
  3. 合同取消以后，`arms:` 清单放在哪，设计没有说。
  4. 合同里原来还有两项，新的简要说明没有对应的位置：停止条件，以及“什么结果对应下一步做什么”。
- 建议：让设计提交带一份机器可读的实验清单，可以就是那个受保护的 arms 文件。清单写明每个臂的名字、seed、关键超参、数据划分和指标。这同样是“代码即设计”，对象从方法换成了实验的定义。
  1. 登记运行时，CLI 按清单核对：臂存在，配置的摘要和清单一致。不一致就拒绝登记，或者登记成“偏离设计”的运行，不能当证据。
  2. 导入结果时，再核对运行自己报出来的实际配置。
  3. 核验行加一行，例如 `arms 6/6 match design, 0 deviations`。
  4. 改清单等于改实验，只有科学家能改，要开新修订版。
  5. 提前停止的条件也写进清单或授权文件（例如 `stop_when`），最好是一个判定函数。否则跑到一半明显不对，研究者按授权只能把剩下的 seed 跑完，科学家要到任务结论才知道。
  
  这样，“用错学习率”就从盼着审核者看出来，变成 CLI 直接拦下。

### 意见 12：“方法还是工程”只靠审核者标一下

- 设计怎么说：审核者给每条发现标类别。方法类必须在交接前由科学家关闭，工程类随任务交给研究者（5.2、5.3）。
- 问题：这个标签决定了谁来修、能不能交接、能不能带着问题开跑。一条本属方法的问题如果被标成“工程、low”，就可以带着它提交作业。设计说明了按严重度分不开两类问题，可是类别同样是一次判断，同样可能标错。
- 建议：加两条机械的规则，流程不用改。
  1. 发现已经带代码定位，实验也记了受保护路径。定位落在受保护范围内的发现，默认算方法类。审核者认为它是工程类时，要写一句理由才能改。
  2. 受保护的单位用符号，不用整个文件。消息设计页的范例里，`src/train.py` 整个文件受保护，而工程类的 F1（检查点路径）也在这个文件里。按整个文件算，研究者普通的工程修补都会显示成“动了方法核心”，核验行里这一行就起不到提醒的作用。定位格式已经支持 `路径::符号`，保护 `src/train.py::masked_loss` 这样的符号更准。

### 意见 13：“第一次运行前封存”没说清是哪一刻；冒烟和调试会被审核卡住

- 设计怎么说：判定函数和预测在第一次运行前随设计提交封存（4.6）。提交作业时，CLI 要求审核覆盖当前提交，并且没有 medium 以上的发现，否则拒绝（9.1）。回合通过后再改受审范围内的代码，要开新回合（6.2）。
- 问题：
  1. 科学家自己的小测试也记成运行。消息设计页的范例 2 里它是 ATT-0228-1；在只能走作业的集群上，它还是一个真的作业。那么“第一次运行”指的是它吗？科学家段里为了修方法问题改代码，算不算封存后的修订？
  2. 冒烟和计时也是作业。照 9.1 的写法，它们同样要等审核通过。而调工程问题的常态是：跑一下冒烟，失败，改两行路径，再跑。每改一次提交就变了，审核不再覆盖，要开新回合，每段又只有两次审核。现在的规则是“冒烟和确定性检查可以先跑”，登记时写 `--no-review "smoke test"` 就行，设计没有保留这一条。
  3. CLI 其实拒绝不了提交作业，因为作业不是它提交的。它能拒绝的是登记运行。
- 建议：
  1. 封存定在交接那一刻。CLI 在交接时记下设计提交，从这时起改受保护范围才算修订，科学家段里的修改不算。
  2. 把运行分成两类。试跑包括小测试、冒烟和计时，时长有上限，不需要审核，结果永远不能当证据引用。证据运行要求审核覆盖，并且和实验清单一致（意见 11）。“第一次运行”指第一次证据运行。
  3. 9.1 的措辞改成“拒绝登记”。导入结果本来就只接受登记过的运行，所以没登记的运行进不了证据。

### 意见 14：作业结束不是数据库里的状态变化，这类待办会丢

- 设计怎么说：通知都由记录的状态变化触发。会话不在或卡住时事项不会丢，因为它还在待办里（8.7、8.8）。“作业结束”列在通知表里。
- 问题：作业结束这件事只有执行器知道。执行器把通知直接发给提交作业的会话，不经过 CLI，CLI 也不去查执行器。通知到达之前，数据库里什么都没变。如果通知丢了，或者研究者会话那时正好断了，数据库里这些作业仍然是“运行中”，谁的待办里都不会出现这件事。8.8 的保证对这一类不成立。
- 现有的补救：等待中的任务 60 分钟没有新消息时，监视会提醒去执行器查。现在提醒的是协调者，11-09 文档 5.3 改成先提醒任务负责人。
- 建议：
  1. 在 8.7 里写明“作业结束”是例外，它不由记录触发。
  2. 提交时把预计结束时间（申请的时长）记在等待上。过了这个时间还没有记录，研究者的待办里就出现一项，例如“T-0042 有 3 个作业超过预计结束时间，去执行器查”。这一项是从记录算出来的，CLI 仍然不用查执行器，也比固定等 60 分钟准。
  3. 研究者会话重启时，启动包第一项列出记录里还在运行的作业，让它先去核对。

### 意见 15：一条记录可能同时等两个人；异常只有“失联”一种

- 设计怎么说：每条记录写明“等谁”，待办从它查询（8.8、10.3）。风险表里列了“待办漏掉某类记录状态”，对策是启动包和待办用同一个查询（第 16 章）。
- 问题：
  1. 一个“等谁”字段不够用。假设任务一直由科学家持有，同时它上面的预算申请在等协调者。任何记录上都可能挂着一条等人答复的提问。同一条记录可以同时等两个角色。
  2. 设计只定义了一种异常：会话失联。更常见的情况是会话还在，但事情没有人动。例如提醒没送到；模型理解错了，以为自己在等别人；协调者自己停在对话框上。新流程里协调者很少运行，它停了以后项目会安静地停住，不像旧流程那样很快有人发现。
- 建议：在“同一个查询”的基础上再走一步。
  1. 把待办定义成一张规则表，每种通知一条规则：什么状态、等谁、要做什么、做完的标志。8.7 的表已经接近这个形式。把它做成代码里唯一的来源，启动包、待办查询和监视都用它。
  2. 加一条不变量，让 `rl doctor` 检查：每条没结束的记录，要么在等某个角色，要么在等一个带截止时间的外部事件。两样都不是的记录，就是被漏掉的。
  3. 待办里的每一项都记“等了多久”。超过期限就按固定顺序往上报：先提醒本人，再报给建任务的一方，再报协调者，最后报用户。“失联”成了它的一个特例。协调者自己的待办超时，直接提醒用户。

## 6. 成本和节奏

### 意见 16：科学家每醒一次，都要把整段对话重读一遍

- 设计怎么说：科学家交出任务后结束本轮，会话空闲时不耗 token，消息到了被唤醒（4.2）。一个假设从建立到判定，中位要 6.3 小时。
- 问题：空闲时确实不花钱，但醒来那一下不便宜。模型服务的提示缓存一般只保留几分钟到一小时。等了几个小时以后缓存已经没了，整段对话要按没有缓存的价格重读。科学家用的是最贵的模型，写过代码以后上下文又长，而它被叫醒往往只为一件小事：读几行核验行，验收一个任务。
- 设计里其实有一条更便宜的路：新会话拿着约 8,000 字符的启动包，从数据库重新开始（4.5、第 11 章）。现在只在会话断了的时候才用它。
- 建议：
  1. 每次唤醒前按一条简单规则选择。空闲超过缓存的保留时间，并且上下文超过某个大小，就不叫醒旧会话，直接按启动包开新会话；否则续用旧会话。新会话要重读它用得到的代码和证据，所以不是每次都更省，阈值用试运行的数据定。
  2. 试运行时，每个科学家在假设中途至少强制重启一次。恢复路径平时很少走，很少走的路最容易坏，会话一出问题又全靠它。常规地走几次，才知道启动包里缺什么。
  3. 这一条和意见 3 的选项 B 是同一个机制：会话可以随时结束，状态都在数据库里。

### 意见 17：小实验也走全套流程，流程比实验贵

- 设计怎么说：每段代码都先过审核，再启动一个研究者会话。每个假设判定前还有结论审核（第 2 章）。
- 问题：消息设计页的范例 7 里提到这样一件工作：换一个评估长度重跑评估，约 0.1 MIG·h。为它开一个审核会话和一个研究者会话，模型的花费会超过它要保护的计算。现在的规则有豁免：已经审核过的规格换 seed，不需要新审核。设计没有写豁免，照字面每个任务都走全套。
- 建议：定一条快速通道，条件都由 CLI 判断，不靠模型自己说“这个很小”。
  - 相对上次通过的审核，受保护范围没有改动；
  - 要跑的臂都在已封存的实验清单里（意见 11），或者只是清单允许的参数变化；
  - 预计花费低于一个小的上限。
  
  三条都满足时，不开新的审核回合，由原来的研究者会话接着跑，或者像科学家的测试作业那样直接提交。有一条不满足，就走正常流程。

### 意见 18：预算不拦可以，但超了要有人知道

- 设计怎么说：预算是努力义务。CLI 不因预算拒绝，只在核验行显示大致用量。预计明显超出时，科学家发预算申请，研究者发授权阻塞（7.2）。这是用户定下的，下面的建议不改变它。
- 问题：
  1. 发现超支全靠模型自己意识到“预计明显超出”。科学家的启动包不含作业细节，协调者平时不运行。
  2. 核验行在交付时才看，那时钱已经花完了。
  3. 没报用量的运行不等于没花钱，但合计里看不出缺了多少。
- 建议：
  1. 加几条只提醒、不拦截的界线，例如信封的 80%、100%、150%。假设任务已记录的用量每越过一条，CLI 就在科学家的待办里加一项，到最高一条时也加进协调者的待办。什么都不拒绝，只保证有人被告知。
  2. 用量除了“已用”，再显示“已登记、还在排队或运行”的部分，按申请的时长估算。还来得及避免的超支在这一部分。
  3. 核验行的用量后面注明有多少个运行没有用量记录，例如 `about 1.2 MIG·h, 2 attempts unreported`。

### 意见 19：八个阶段做完才第一次试运行

- 设计怎么说：实施分 0 到 8 阶段，第 8 阶段才试运行（第 15 章）。第 17 章列了没验证的事：科学家写代码以后的 token 用量没有数据，消息量的目标没有实测，300 字符的上限没有试过。
- 问题：最没把握的几件事都是“模型会不会照这样工作”，不是“软件做不做得出来”。强模型写实验代码和判定函数，花费和质量怎么样？方法和工程分不分得开？审核者标的类别靠不靠得住？这几条如果不成立，前面七个阶段做的数据模型和检查都要返工。
- 建议：
  1. 在阶段 0（计量）之后插一步：手工试一个假设。用现在的插件，靠口头约定按新分工走完一个小假设，一个科学家会话写代码和判定函数，配一个审核者和一个研究者。数三样东西：各角色的 token，研究者回头找科学家的次数，标错类别的发现数。几天就能知道主线成不成立。
  2. 调整顺序，先做在旧流程里也有用的部分：核验行（阶段 3）和从状态查待办（阶段 4 的一部分）。它们不依赖科学家角色，做完马上能给现有项目减负，也能早点暴露待办规则的遗漏。
  3. 给进行中的项目定一条切换规则：挂在假设任务下面的任务（有 `PART_OF`）按新规则检查，没有挂的按旧规则。这样一个跑到一半的项目可以一个假设一个假设地换到新流程，不用选一天全部切换。没关闭的旧审核回合里，发现没有类别，也按旧规则处理。

## 7. 文档里的小问题

- `DESIGNED_IN` 多余，创建顺序也绕。设计和实现并入执行任务以后（第 14 章第 10 项），实验用 `DESIGNED_IN` 指向任务，任务又用 `TARGETS` 指向实验，通常是同两条记录互相指。实验要先存在才能被任务指向，它的设计提交却要等任务里的代码写完才有。建议去掉这条边，“在哪个任务里设计的”取第一个指向它的执行任务；并写明顺序：短决定、实验（草稿）、任务、代码、记下设计提交、交接时封存。
- 关系页还是旧模型：有设计任务，协调者建执行和准备任务，协调者验收。设计说了冲突时以整合文档为准，但站点把两者放在一起，读的人会混。建议重画，或者在冲突的格子上标“已被取代”。
- “说明最多 2 句”不好让机器判断。中英文标点混用、小数点和缩写都会把句子数错，每一次误拒都让模型白跑一轮。300 字符的上限已经够用，建议只查字符数。代码定位里的符号检查同理：先只对 Python 文件查符号，其他文件只查路径。
- 结论审核请求里的说明会带偏审核者。消息设计页的范例 8 里，科学家写的是“重点看该判挑战还是不确定”。审核者的启动包特意不放作者的说法，为的是独立判断，这一句又把作者的看法带了进去。建议结论审核的请求不带说明，或者只允许指向记录。
- 一句结论里手抄了数字。消息设计页范例 6 的 `T-0042.conclusion` 写着“高 0.4 点（+1.5、-0.2、-0.1）”。这些数字在结果和证据里已经有了，和“一条事实只存一处”不一致，补跑或更正以后还可能对不上。建议结论只写方向并引用证据，数字在读取时从判定表展开。
- 研究者没有“只想问一句”的通道。它发给科学家的只有任务结论和两种阻塞（8.3）。“这里是有意这样写的吗”既不是要改设计，也不是超出授权。没有出口的话，它要么被包装成设计阻塞，要么由研究者自己猜。审核者有审核讨论，协调者有提问。建议给研究者一种最轻的阻塞原因“疑问”：科学家答一句，记在任务上，任务回到执行中。
- 协调者验收假设结论，多半是机械的。核验行上的每一项（结论审核通过、封存早于运行、任务都已验收），CLI 自己就能判断。建议把这些做成交付的前提，不满足时 CLI 直接拒绝交付。协调者被叫醒以后只做需要判断的那件事：看建议的下一步，排下一个假设。

## 8. 建议保留的部分

- 待办从记录状态查询。提醒丢了、被截断、会话重启，都不影响该做的事。这是设计里最稳的一块。
- 代码即设计。判定函数在看到结果之前写好并封存，比文字合同更难事后调整。
- 机械事实由 CLI 算出（核验行），模型只做解释和路线判断。
- 改假设状态之前必须有独立的结论审核，由 CLI 把关。
- 从数据库恢复，文档挂在记录上，不再有越写越长的交接文档。
- 文档自己的写法：每条决定带日期，待确认和没验证的事单独列出。评审时很容易分清哪些已经定了。
