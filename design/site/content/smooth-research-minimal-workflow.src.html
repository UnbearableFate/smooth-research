角色

每个角色只回答一个问题

科学家

一个假设一个科学家会话，交出结论就结束

一个科学家负责一个假设，或者一组放在同一个实验里检验的假设，再加上它为这个实验拆出的子假设。在这个范围里，需要什么实验、什么任务、写什么代码，都由它决定。每开一个新实验，它先写一条短决定，实验用 MOTIVATED_BY 指回这条决定。对话断了，或者监视清掉对话重开，新对话都持同一个假设任务启动，从这些记录接着做，不需要交接文件。假设之间的前提关系记成边，上游的结论变了，CLI 会通知受影响的科学家；它决定停的，交一条“停止”的假设结论，不判定，只把假设改成暂停或退役。

拆树时规则
科学家交回的东西假设记录，每个有命题、范围、出自计划哪一节，和一句目的：检验它是为了回答什么（purpose，研究页用）；没进树的内容和理由；公共的准备任务清单；每个假设的大致花费和先做哪几个的建议；一条记下为什么这样拆的决定
公共的准备任务科学家只列出；协调者接收树时把它们建成项目下的排队任务，算进第一阶段，用户批准后和假设任务一起放行
树的深度只拆到一个便宜的实验能检验为止，远的分支标成候选；更细的子假设等结果出来再派生
查文献科学家用自己会话里的子代理去搜和读，核对以后自己记录。说一个假设已经有人做过，至少要读过那篇论文的相关部分
新颖性或可行性不足科学家不删改这个假设。它打上标记，写明缺哪一样、依据和选项，随树交回协调者；协调者转给用户决定。核心主张被标记时，不必把树拆完，先交回
审核的四个问题每个假设是不是可以检验的命题；有没有漏掉明显的竞争解释；计划里的每条主张有没有对应；新颖性和可行性的判断有没有核对过的出处
审核过不去三次后仍有 medium 以上的发现，交给顾问裁决

同一个科学家设计、写代码、再判定，就有事后改门槛的风险。所以判定函数、预测和实验清单在交接时随设计提交封存，要改就开新修订版并写明原因；改假设状态前还要独立的结论审核（图 10），请求不带作者的说明。

代码

代码就是设计：科学家写实验代码和判定，研究者修工程问题

科学家交出五样东西：任务分支上的设计提交；挂在实验上的简要说明；固定方法和判定含义的语义测试；机器可读的实验清单；受保护范围清单。实验的定义以设计提交里的代码和实验清单为准，说明只留不读代码也要知道的部分，不再写长合同。

科学家只跑 CPU 上、玩具尺寸、几秒钟跑完的测试；真实模型上的 A0、冒烟和计时都归研究者。如果小测试也只能走作业（例如 Miyabi 的登录节点不跑负载），科学家提交一个短作业，结束通知只带通过或失败。小测试、冒烟和计时都算试跑：不用等审核，时长有上限，结果不能当证据。实验清单里的臂才是证据运行，登记时 CLI 核对审核和配置。

交接

一段代码一个任务，审核回合跟着任务走

科学家建任务后先持有它写代码，任务的分支 sr/T-xxxx 和工作树从这时开始，工作目录 research/work/T-xxxx/ 在工作树里。交接时持有者换成研究者，分支、工作树和开放的审核回合一起转过去，研究者的会话直接在任务的工作树里启动。研究者交任务结论后，科学家读核验行验收：CLI 先把任务分支和当时的主线合成一个合并提交，在它上面跑语义测试，通过了才把主线移过去；不接受就退回，研究者接着做。登记成产出的小文件要提交在任务分支上，交付时 CLI 检查，不然删掉工作树就丢了。

结论审核：改假设状态、停一条路线或推荐正式实验之前，科学家开结论审核。审核包由 CLI 从记录生成：决定草稿、引用的证据、封存的预测和判定函数的修订版、核验行。科学家不另写材料，请求也不带说明，免得把作者的看法带给审核者。没有通过的结论审核，CLI 不接受改假设状态的决定。三次后仍未通过，由顾问裁决：撤销的发现按裁决关闭，维持的发现要改。

任务谁写代码审核怎么验收
执行任务科学家写，研究者修工程问题科学家段和研究者段，每段最多三次科学家读核验行；验收即合并，先在合并提交上测
快速通道代码不变，或只在受保护范围外改不开新回合。条件由 CLI 判断：受保护范围没改，臂在实验清单里，花费低于小上限。运行仍由研究者做，续用上一个任务的研究者会话，或新开一个；科学家不自己提交同执行任务
准备任务研究者写；科学家只写要求和一条检查命令产出里有后面实验要用的核心代码时才审检查命令通过
公共的准备任务研究者写；拆树时只列出，协调者接收树时建成项目下的排队任务，用户批准后放行同准备任务；阻塞和研究者段的升级进协调者的待办，由它交给一个短的科学家会话检查命令在交付的提交上通过，CLI 就验收并合并，不需要科学家判断

已验收的准备任务产出、公共基线和数据版本登记成可复用的产物，每个一行，进科学家的启动包。在新的代码区域写第一个实验之前，先开一个准备任务，让研究者交一份环境事实清单：模块名、张量形状、单批显存、单步耗时。

落到代码：现有 handoff 是同一个角色换会话的旧做法，要求一份交接文档，释放任务，并默认给协调者发 HANDOFF。新版本不兼容旧项目（11-25），rl task handoff 和按会话建的工作树一起删掉。新的交接用 rl task dispatch；它不带新文档，因为说明已经挂在实验上；也不发消息，由监视为任务启动研究者会话。同一个角色换一段对话或换模型叫换人，新对话从启动包恢复，不写交接文档。审核单要记下所属任务、当前段和每条发现的类别；_route 改为把回合交给监视，在 herdr 的面板里启动会话，会话名取自审核单 id；无头的 rl review run 删掉。工作树改成按任务建（worktrees.py），验收时由 CLI 先测再合并。

沟通

有结论、收件人要行动，才发消息

状态和进度写进研究数据库，读完什么都不用做的消息不发。每条消息都有类型，只带主记录、ask、定位和一句说明；通知不存成消息，待办从记录状态查询，详见消息设计页，每种消息的具体内容见那里的范例。

检查

CLI 在十五处检查，预算只显示不拒绝

机械事实由 CLI 算出，模型判断解释和路线。验收时读 CLI 生成的核验行，必要时按 id 抽查证据。

写对话条目每个定位能解析；定位不超过 8 个；正文不限长拒绝写入

启动

每个角色启动时只载入一个启动包

用户不是 agent。用户提供目标、预算和必须先问的事，先批准假设树和第一阶段的排期，批准之前 CLI 拒绝放行；之后看研究页上的阶段报告，答复转来的决定请求，阶段报告不挡下一阶段。用户不运行写命令：答复都在协调者的面板里说，由协调者用 rl request answer --by user 记下；用户不在时，事项留在用户的待办里。用户运行 rl resume 把项目接着跑起来：它确认 herdr 里有协调者的面板（没有就开一个，从启动包启动）、监视在运行，并打印项目状态和等用户决定的事；没有 herdr 时它拒绝启动。用户从下表的三处了解项目。每个启动包的具体内容和范例见启动包页。
