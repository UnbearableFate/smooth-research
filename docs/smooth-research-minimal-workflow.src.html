角色

每个角色只回答一个问题

沟通

有结论、收件人要行动，才发消息

状态和进度写进账本。读完什么都不用做的消息不发。每种消息和任务包的具体内容见样例页。

审核

一个回合一个会话，谁请求谁启动

rl review request 一条命令建审核单并启动会话。模型由 CLI 按配置选，请求者不能指定。每个任务同一时间最多一个开放回合，所以不需要排队和上限。

落到代码：_route 改为调用 open_session；审核单记下所属任务；_round 加新回合检查；会话名取自审核单 id，避免 _free_name 在并发时重名。

启动

每个角色启动时只载入一个启动包

用户不是 agent。用户提供目标、预算和必须先问的事，之后只看阶段报告和决定请求。

现有 work_pack 已接近研究者的启动包。resume_pack 给协调者时要去掉未完成 attempts、Locations 和 Compute 三节。科学家的启动包要新写，从数据库读假设树、最近的决定和待判定的证据。

怎么回答协调者的自由提问固定类型“答复”：引用那条消息的 id，每条最多答复一次
研究者要不要开新会话每个任务开新会话，只靠启动包；退回或阻塞解除时回到原会话继续同一任务；取消“不压缩直接继续”
实验由谁设计科学家：单独的长期会话，更新假设、设计实验、请审核、写决定（11-09）
协调者核查设计看什么只看是否符合计划、用户约束、预算和优先级、审核状态；方法问题由审核者和科学家解决（11-10）
设计不成立的阻塞发给谁直接发给科学家，不经协调者；直接发要 2 条消息，经协调者要 4 条（11-10）
工作文件放在哪任务的工作目录 research/work/T-xxxx/，交付时把要留的文件登记成产出；协调者不持有任务，没有工作目录（11-10）
