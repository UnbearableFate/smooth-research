## A · Local-trial blockers

1. **High · A recheck on the same ticket fails to wake the reviewer or author.** I drove both tree and researcher design reviews through failure, notification, recheck and pass. On recheck, the idle reviewer received no new prompt. After I supplied the pass, the author's inbox showed the new verdict, but the idle author received no prompt either. The watcher had already marked the same ticket keys as delivered for the previous pass and could suppress them until the default four-hour reminder. Include the pass number in the delivery identity for both requests and verdicts. `reviews.py:200–213`, `inbox.py:44–45,260–295`, `watch.py:215–222,245–250`
2. **High · An older tree pass can authorize delivery over a newer failure.** After one passed round, I opened another and recorded a high-severity finding. The scientist simultaneously received instructions to deliver the tree and to fix it. Delivery and coordinator acceptance both succeeded with the finding open. Make the inbox and delivery guard consult the same latest applicable tree round. The researcher variant also needs a clearing condition. Its passed verdict remained after evidence registration and prompted the researcher again at the reminder deadline while the job was running. `inbox.py:282–295`, `reviews.py:117–121`, `tasks.py:626–628`, `watch.py:245–250`
3. **Medium · Updating an in-progress schema-5 project invalidates unchanged clearances.** I opened two projects written by `081d80f`. An untouched draft failed dispatch and, after a fresh test, still required a new review. A previously dispatched task that had already registered evidence could no longer register another run. Adding `edit_seq: null` to the digest changes the stored identity before the first edit. Preserve the original digest for records with no edit sequence, then include the sequence from the first edit onward. This affects trials resumed across the update. `research.py:267–269,370–385`, `tasks.py:429–437`, `reviews.py:74–78`

## B · Before job-mode or remote use

1. **High · An older sync can delete or overwrite the newer round's published candidate.** I paused a sync with an empty desired set, started an acceptance and let a second sync publish it. The first sync then listed the *new* tip and successfully deleted it with a lease. In the reverse case, an older publisher force-pushed the previous round's commit over its successfully published replacement. In both cases a fresh worker clone lacked the active round's commit. Serialize reconciliation per project and destination, and recheck the committed round before applying a stale snapshot. Use an expected remote tip for replacements as well as deletions. `compute.py:399–418`
2. **Medium · Retirement queries the fetch URL and ignores listing failures.** With separate local bare fetch and push repositories, publication reached the push destination. After cancellation, sync inspected the empty fetch repository and left the retired ref at the push destination. Making the fetch URL unavailable also yielded an empty problems list. Enumerate each actual push destination and surface a failed or timed-out listing. `compute.py:401–417`
3. **Medium · A corrected attempt can still reject its round.** After the failure handler read a terminal failure, I recorded an explicit correction to `running` before its conflict write. The handler rejected the round using the stale failure. The attempt subsequently succeeded, but the task stayed delivered and main never moved. Route failed and successful observations through one write-locked decision that reads the current attempts. The same path can avoid committing a write for an unchanged wait. With one success and one running retry, three otherwise idle watcher beats changed the database version and regenerated the page three times without adding an event. `tasks.py:819–830,859–887,895–906`, `runs.py:337–344`, `store.py:429–436`, `watch.py:365–375`
