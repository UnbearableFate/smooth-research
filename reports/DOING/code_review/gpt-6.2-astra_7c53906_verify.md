## A · Local-trial blockers and their conditions

1. **High · A new tree review can fail between delivery and acceptance.** The scientist can open another review after delivering the tree because the request checks the holder and kind only. I passed the first round, delivered, opened a second round with a high-severity finding, then successfully accepted the tree as coordinator. The scientist still had a “fix” item on the accepted tree. Opening a new review after acceptance also succeeded. This pre-existing path remains outside the repaired delivery guard. Require an active tree task for a request or recheck. A delivered tree with further work should first be returned. `reviews.py:153–158`, `tasks.py:627–628,689–693`

2. **Medium · A researcher verdict can disappear before work resumes or outlive the work it requested.** An evidence registration immediately *before* a pass, in the same UTC second, suppressed the verdict. Conversely, registering a retry *after* the pass left the verdict visible because the original Run retained its creation time. I also opened a second design round before registering evidence. After it failed, the inbox simultaneously said “go on” and “fix”, while the evidence command correctly refused to run. Derive the item from the latest applicable round and compare the ordered `review.answered` and non-test `run.register` events. Each new attempt already emits the latter. `inbox.py:275–281,295–306`, `util.py:30–31`, `runs.py:158–190`, `store.py:262–265`

3. **Medium · An unchanged handover cleared by the immediately preceding version loses that clearance.** I reopened an `081d80f` project under `298955e`, retested and re-reviewed the unchanged draft, dispatched it and registered evidence. At `7c53906` the next valid evidence registration failed with “draft changed”. The middle version hashed an explicit null edit sequence. This version omits the field. For an experiment that has never been edited, recognize or migrate both exact historical digests. Keep sequence matching strict once an edit exists. `research.py:373–383`, `reviews.py:74–78`, `runs.py:196–207`

4. **Medium · Resume can start a second coordinator immediately after the watcher recovered the first.** I let the watcher rebind the live coordinator between resume’s lookup and its write. Resume treated the already-open record as a failed lookup, opened another tab, reported “name taken” and recorded a newer failed session. The original agent remained usable. Return the concurrently recovered binding to the caller and recheck the open record before reserving a new launch. An older recovery hazard also remains when an open row has a stale pane ID but its owned tab still contains the live agent. Resume closed that tab and started a fresh conversation. Resolve the agent by name before closing the owned tab in that case. `watch.py:235–265,369–375,461–484`, `launch.py:126–161`

5. **Medium · The latest-record lookup reverses at the four-digit ID boundary.** With the fixture counter advanced to the boundary, the CLI allocated `RV-9999` and `RV-10000`. After the first passed and the second failed, the inbox offered delivery and the coordinator accepted the tree with the finding open. Session recovery similarly rebound `S-9999` to the live conversation belonging to `S-10000`. This affects long-running projects. Use the numeric order already supplied by `Tx.all` and share the latest-tree selection between the inbox and the delivery guard. `reviews.py:117–126`, `inbox.py:307–313`, `watch.py:241–249`, `store.py:126–129,171–180`

## B · Job-mode and remote blockers

1. **High · Sync can report success while omitting a configured push destination.** The helper parsing Git’s URL list receives only the last 400 characters of combined diagnostic output. With three valid bare push repositories, ordinary branch publication reached all three. Candidate publication reached the last two. Sync reported no problems, and a fresh clone of the first repository lacked the commit registered for the job. Read complete stdout for successful URL enumeration and truncate only displayed diagnostics. `compute.py:363–370,391–395,442–448`

2. **High · Candidate sync prints credentials embedded in a push URL.** With a clean fetch URL and a separate HTTPS push URL containing a synthetic credential, a successful simulated transport put the credential in the sync summary. Listing failures, publication and retirement messages all interpolate the raw push URL. Use a credential-free destination label in output and redact URLs in Git diagnostics before displaying them. `compute.py:447–451,459–469,552–553`

## Architecture and validation

The merge path now makes one decision from the current attempts under the write lock. Candidate reconciliation has a single per-project owner and uses Git leases at the destination. The remaining duplication with a demonstrated cost is the selection of the current review in the inbox and command guards. Sharing that selection would remove two independent ordering rules.

All **110 repository tests passed**. **48 disposable verification cases** exercised CLI role flows, three code versions against persisted stores, fake Herdr panes, real local Git destinations and separate sync processes. Pyflakes and Ruff’s `E9,F401,F63,F7,F82` checks passed. Live agent hosts and a remote scheduler were outside this verification.

The highest-value permanent regressions are a review opened after tree delivery, a retry and a same-second registration on opposite sides of a verdict, a handover cleared by `298955e`, concurrent watcher/resume recovery, and multi-URL sync checked from each worker clone. Include credential redaction on both success and failure paths.
