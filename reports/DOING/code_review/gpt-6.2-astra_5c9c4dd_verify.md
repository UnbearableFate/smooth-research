# Schema 5 workflow verification, round four

**High-severity issues remain before the live trial.** A passing test on one manifest authorized evidence on a different manifest that failed the same test. Recovery can still accept a task while its only merge test is running. An interrupted acceptance can also leave a remote worker unable to fetch its assigned commit.

## Design review and test results

**R4 · Reviewer pack and finding classification — fixed.** A researcher requested review while holding revision 1 and the scientist had opened revision 2. The ticket and pack both identified revision 2. Editing its question and protected scope after the request left the pack unchanged. The reviewer still had to justify an engineering finding in the originally protected file, and the verdict did not clear the edited draft. `reviews.py:74–78,169–174,204–208,226–233,281–287`, `pack.py:289–299`

**R4 · Draft edits and test clearance — partly fixed, high.** Switching manifests within one commit and draft now invalidates the scientist's previous review and test. The remaining failure occurs while a researcher still holds the earlier handoff. I ran a semantic test that read the manifest selected for that task. Its output recorded the original manifest and `k=1`, but the pass was stored under the new draft's key. After the blocker answer and a valid review of the new draft, I ran the identical command as an independent check. It failed on the replacement manifest with `k=19`. The workflow still considered the earlier pass sufficient for dispatch, and an evidence run registered with `k=19`. Local tests and job registration both take the command from the task's design and the key from the live experiment. Derive the command and key from **one snapshot in one read**. A researcher testing their sealed handoff must credit that handoff. `tasks.py:239–245,273–275,302–319,405–412`, `runs.py:118–124`, `research.py:360–383`

**Medium · The draft key contains only 16 bits of digest.** The 12-character slice includes the eight-character `blake2b:` prefix. I verified that the stored key retained four hexadecimal digits. Two different drafts of the same revision can therefore share clearance even when their full digests differ. Store the full digest for equality checks and shorten it only for display. `research.py:368–378`, `util.py:43–44,59–64`

**5 · Same-second ties — fixed. End-time ordering — partly fixed, high.** A tied failure blocked dispatch in both reporting orders. A later successful job cleared it. Across distinct seconds, `closed_at` is the time the CLI received the terminal observation. I supplied two observations from one executor with explicit event and observation times. The later failure arrived first. The older success arrived last and authorized dispatch, even though its manual test report was entered first. Use the executor's trusted completion order when available and require a fresh pass when conflicting observations cannot be ordered. `runs.py:332–336,364–368,454–465`, `tasks.py:294–296,327–342`

## Acceptance and remote staging

**R1 · Already-contained delivery and live job — partly fixed, high.** With a stable mainline, an already-contained delivery was accepted immediately in both local and job modes. A registered running job also blocked recovery when it was visible at the initial check. Two separate reads still leave a race. Using the external fast-forward from the repository's own recovery regression, I registered and started the round's first job after recovery read the attempt list but before it wrote acceptance. The watcher accepted the task with zero successful attempts. Recording the job's failure left it accepted. For job-mode recovery, require a successful attempt for that round in the transaction that accepts it. For the initial containment shortcut, carry the ancestry decision out of candidate construction. Advancing main between its two reads also made an already-contained delivery request an unnecessary job. `gitops.py:182–186`, `tasks.py:703–723,736–752,765–779`

**R1 · Public prep interrupted before candidate registration — partly fixed, high in job mode.** Local recovery waited through the grace period and completed prep after interruptions on either side of candidate registration. In job mode the watcher restarted the merge, then left the task `merging` with no merge-test attempt and no inbox item for its researcher. A second beat did nothing. The registration instruction is returned to the watcher, which discards it. Manually registering and completing the job accepted the task. Derive an inbox item for the submitter while a required merge test has no attempt for its round. `tasks.py:718–726,833–855`, `watch.py:307–315`, `inbox.py:203–215,220–231,325–331`

**Remote refs · Publication and retirement — partly fixed, high.** In the original competing-accept case, the losing transaction preserved the winner's branch and the bare origin received its candidate. The second-round staging instructions now call the working `rl compute sync` command. Ordinary cancellation removed the local ref. A return during local testing also survived the late result. Job-mode `task return` still refuses tasks already in `merging`. `tasks.py:708–726,876–892`, `compute.py:261–272,450–454`

- **Publication can be lost.** I interrupted acceptance after the database committed `merging` and before `name_candidate`. After restart the watcher left the ref missing, retrying acceptance was refused, and sync left the registered commit absent from the origin. When I cancelled in that same gap, the delayed publisher created a branch for the cancelled task and sync pushed it. Reconcile the local ref against the persisted round before staging and serialize publication with changes to that round. `tasks.py:228–232,666–669,718–726,829–855`, `gitops.py:204–217`
- **The expected commit does not identify the round.** An immediate retry with identical parents, message and Git timestamp produced the same commit in two rounds. Delayed cleanup from the first failed round deleted the second round's ref, leaving its candidate absent from the origin after sync. Use a per-round ref or verify round ownership under the same lock as deletion. Also retire the ref when the fast-forward fails. Advancing main during a successful test left the rejected candidate in the next push. `gitops.py:192–211`, `tasks.py:771–780,797–805`

## Validation and test gaps

All **93 repository tests passed**. I ran **30 additional disposable cases** against the CLI, real Git repositories and LatticeDB stores, using controlled interruption points, a local bare origin and a fake Herdr for watcher checks. The live plugin trial was outside this verification. CodeGraph supplied caller traces. Pyflakes was clean. Ruff 0.17.6 passed `E9,F401,F63,F7,F82`. Its full configured run reported 80 diagnostics.

The review pass now gives the pack and finding classifier a single snapshot. Tests can use the same approach, and the persisted acceptance round can own both Git ref reconciliation and the submitter's inbox item.

The highest-value regression tests are the manifest-sensitive test across a handoff, out-of-order terminal observations, registration during recovery's final write, and restart after the database commit but before Git ref creation. Include job-mode public prep and same-commit retries. Assert which manifest actually ran, which round owns the fetchable ref, and which submitter receives the next action.
