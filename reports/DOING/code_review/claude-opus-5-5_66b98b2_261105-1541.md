## Findings

### 1. Medium: a headless review worker overwrites an answer recorded while it ran; the "answered once" check is outside the write

- Location: `src/smooth_research/reviews.py:302-307` (`run_ticket`, failure path) and `:333-344, :362-371`
  (`_store_answer`).
- Problem: `run_ticket` marks the ticket `running`, then calls the configured models for up to `timeout`
  (30 min by default). Meanwhile a reviewer session (`rl review answer`, `answer_live`) or an import
  (`rl review import`) can answer the ticket: `_store_answer` refuses only `status == "answered"`, and `running`
  is not that. When the worker's candidates then fail, it writes `status: failed|unavailable`, `calls` and
  `error` unconditionally, over the answer. Separately, `_store_answer` reads the status in a read
  transaction, writes `research/reviews/RV-x.md` and seals it, and only then opens the write transaction, which
  does not look again: two answers that arrive together are both recorded, and the second replaces the first's
  file, `answer_ref`, verdict and severity (advice revisions compute the same revision file name the same way).
- Evidence: the failure write is `tx.update(ticket_id, {"status": status, "calls": calls, "error": ...})` with
  no re-read; `review_passes` requires `status == "answered"`.
- Impact: a passing review silently stops passing (run coverage falls to "not reviewed", a key conclusion stays
  in attention with no visible cause), or the ticket that the skill calls final ("a ticket is answered once")
  carries the later of two answers. The record of the overwritten answer survives only as an orphan
  DocRevision.
- Fix: in `_store_answer`, re-read the ticket inside the write transaction, refuse there, and compute the
  answer file name and write it inside that transaction (the object is still written before the commit, so the
  crash rule of `documents.py` holds). In `run_ticket`'s failure path, re-read the ticket: when it was answered
  meanwhile, keep the answer and only append this worker's calls. Test both orders.

### 2. Medium: `rl hypothesis set --evidence-status supported|challenged` records a key conclusion with no decision and no review

- Location: `src/smooth_research/research.py:180-189` (`set_hypothesis`), CLI at `cli.py:691-696`; the gap
  check is decision-based (`research.py:732-742`, `key_hypotheses`).
- Problem: the skill makes "a hypothesis set supported or challenged" a key conclusion that needs a passing
  conclusion review and stays in attention until it has one. That is tracked only for `rl decide
  --set-evidence-status`: decide records the conclusion even without the review, but reports the review gap and
  keeps it in attention (a reminder, not a hard gate; wording corrected after the GPT-6 cross-check).
  `hypothesis set` accepts the same two statuses, writes them directly, and nothing (attention, report, page)
  notices: the page then shows the hypothesis as supported.
- Evidence: `KEY_STATUSES = ("supported", "challenged")` is consulted only through decisions;
  `set_hypothesis` takes any `evidence_status` from `ENUMS`. The command is discoverable through `--help`, so a
  coordinator agent can reach it.
- Impact: the review tracking the plugin keeps on key claims (review gap, attention) is bypassed by an ordinary command.
- Fix: refuse `supported`/`challenged` in `set_hypothesis` with a pointer to `rl decide --targets H-x --action
  continue --set-evidence-status ... --based-on EV-x,RV-x`; other statuses, dispositions and `--rechecked` stay.
  Existing records are not touched.

### 3. Medium: arm tables average runs whose `environment_ref` differs

- Location: `src/smooth_research/view.py:106-111` (`condition`).
- Problem: a row groups runs by contract revision, arm, data, model, config and params. `environment_ref` (the
  lock, the extra, the modules) is not part of it, so a CPU run and a CUDA run of the same arm are averaged into
  one mean. workflow.md says "Runs with a different environment_ref are not the same comparison".
- Impact: every place that shows the tables (page, report, manuscript, conclusion review packages via
  `_arm_table`) presents a mean over incomparable runs. A conclusion reviewer cannot see the mixing.
- Fix: add the environment to `condition` (and to the `varying` columns), so such runs get separate rows and the
  table names the differing environment. Grouping of projects whose runs share one environment is unchanged.

### 4. Low: `--read-only` writes `research/state/config.last-read.json`

- Location: `src/smooth_research/project.py:540-544` (`load_config`), called from `find_project` before
  read-only is known.
- Problem: when `smooth-research.yaml` changed since the last command, any command, `--read-only` included,
  rewrites the cache. workflow.md: "`--read-only` changes nothing: ... no record, file or cache written".
- Evidence: reproduced: `rl status`, edit the config, `rl --read-only status`: the cache file changes. The
  existing test only compares files without editing the config in between.
- Fix: thread a `write_cache` flag (`find_project(..., read_only=...)` → `load_config(..., remember=False)`).

### 5. Low: `rl export --records-only` output is not the snapshot it promises when there are warnings

- Location: `src/smooth_research/cli.py:165-167` and `:1078-1087`.
- Problem: plain output prints the JSON and then `warning: ...` lines on stdout, so `rl export --records-only >
  snap.json` is invalid JSON whenever a configuration warning exists; with `--json`, `main` adds a `warnings`
  key into the snapshot payload itself.
- Evidence: reproduced with an invalid model entry in `models.reviewer`.
- Fix: for a command whose output is data, print warnings to stderr and do not merge them into the payload.

### 6. Low: the watcher can leave a session it should watch

- Location: `src/smooth_research/watch.py:856` (`run`).
- Problem: a beat reads the sessions, then (seconds later, after herdr calls) clears `watch_tab` when it saw
  none and exits. `rl agent open` records the session's `herdr_agent` and then calls `watch.start`, which sees
  the registered tab with a fresh beat and does not start another. If the open lands between the beat's read and
  its write, the new session runs without a watcher until the next `agent open`.
- Fix: decide "no session" inside the write that clears `watch_tab`: re-read the active herdr sessions there
  and keep running when one appeared.

### 7. Low: two sources of truth for Codex's home directory

- Location: `src/smooth_research/adapters.py:151, :167` vs `src/smooth_research/usage.py:51` (and
  `agentlog.locate`).
- Problem: `adapters` uses `os.environ.get("CODEX_HOME", default)` without `expanduser` (an empty value means
  the current directory, `~/x` is taken literally); `usage`/`agentlog` use `or` and `expanduser`. The model a
  headless Codex call ran (`_codex_rollout_model`) and the sandbox choice can thus read another directory than
  usage and the watcher read.
- Fix: one helper (`usage.codex_home()`), used by all three; `_codex_rollout_model` can use `agentlog.locate`.

## Candidates that did not survive

- `compute.sync` checks the host for the commit only when some push succeeded: when none did, the problem is
  already reported; no wrong result.
- `Tx.unlink` passing `None` for a missing record: its only caller (`runs._bind` correction) has both records.
- `runs.register` seals the contract before the request dedupe: a retry of the same request only fails if the
  contract became invalid in between; the dedupe itself is inside the write. Not worth a change.
- `prepare_advice` dedupe outside the write: only the coordinator prepares advice rounds; no concurrent path.
- `--base` is used only on the first worktree of a session (`switch_task` uses the main checkout): matches
  team.md ("made from the branch of the main checkout (`--base` picks another)"), arguably per-open.

## Summary

- Architecture: clear module boundaries (records in `store`/`research`/`runs`/`reviews`, session control in
  `agents`/`watch`/`herdr`, read models in `view`/`explain`/`manuscript`), one process lock and one transaction
  per write, content-addressed sealed documents, explicit additive migrations with frozen fixtures. The recurring
  weakness is check-then-act across a read snapshot and a later write (findings 1 and 6): invariants that a
  concurrent session can break must be checked inside the write transaction.
- Simplification: one Codex home helper; one place that decides where warnings go for data-producing commands.
- Missing tests: concurrent answer paths (worker vs session vs import), `--read-only` after a config edit,
  environment-split tables, `hypothesis set` with key statuses, `export --records-only` with warnings, the
  watcher's exit with a session opened during the beat.
- Verdict: sound and well tested for the single-actor paths; fix findings 1-3 before relying on unattended
  multi-session runs, the rest are cheap hygiene.
