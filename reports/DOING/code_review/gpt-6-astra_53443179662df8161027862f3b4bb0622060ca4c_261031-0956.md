**Architecture and execution paths**

The project is a local research record and coordination system. Its main state owners and boundaries are:

| Area | Ownership and execution |
| --- | --- |
| Project, schema, store, documents | The main project owns the LatticeDB graph and sealed document objects. A researcher's checkout supplies source files but shares the main record store. `Store.read/write` combine filesystem locking with database transactions; IDs, request identities, schema checks, and graph relation constraints live here. Documents are sealed before their references are registered, so an interrupted operation can leave an unreferenced object rather than a reference to a never-written object. |
| Research and runs | Hypotheses, experiment contracts, evidence, and decisions describe scientific intent and judgments. Run specifications and attempts record execution identity; observations, result imports, and usage describe external execution facts. The external execution tool owns jobs. Missing observations do not authorize retrying jobs. Shared projections feed reports, manuscript material, and conclusion packages. |
| Reviews and advice | Packages are sealed and tickets hold model candidates, calls, answers, and workflow state. Adapters invoke installed hosts or request manual submission. A worker claims a ticket inside a write transaction; background launchers no longer overwrite completion. Review qualification is centralized in `review_passes`, making errors in ticket state consequential across several consumers. |
| Tasks, sessions, and watching | Tasks own claim/progress/acceptance state. Sessions own host identity, assignments, and worktrees. `messages` records messages before attempting notification; `worktrees` owns Git operations; `launch` owns host startup and dialog selection. The watcher observes sessions and external facts and shares startup with explicit agent opening. |
| Context, distribution, and recovery | `open_work` supplies status, resume, and SessionStart context. The shared contract reader supplies work/review packages and manuscript generation. Shared plugin content is combined with host substitutions by the packaging script. Snapshots restore records and sealed documents, without querying or restarting external work. |

The 27 Python modules contain 7,234 source lines. Static analysis of their internal imports found no cycles. The extracted `scope`, `messages`, `worktrees`, and `launch` responsibilities fit their callers; the shared startup, contract reading, and status paths remove the earlier competing implementations. The current tests exercise real graph storage, Git worktrees, document sealing/restoration, executor fixtures, and fake-host process behavior, plus the new installed-host help checks.

The remaining problems are mainly mismatches between a record's identity and the state attached to it: approval belongs to an answer, a review limit belongs to a whole round, an advice cache key must describe its package, and an existing relation can still have mutable metadata.

**F1 — P1 / high: importing a replacement review answer retains approval of the earlier answer**

**Location:** [reviews.py:345](/home/yu/workspace/smooth-research/src/smooth_research/reviews.py:345), particularly the update at lines 347–354. Entry path: [import_answer:377](/home/yu/workspace/smooth-research/src/smooth_research/reviews.py:377). Consumers: [research.review_passes:344](/home/yu/workspace/smooth-research/src/smooth_research/research.py:344) and [scope.code_coverage:157](/home/yu/workspace/smooth-research/src/smooth_research/scope.py:157).

**Problem and execution path:** `rl review import` accepts a ticket that already has an answer. `_store_answer` replaces its answer reference, verdict, severity, and other outcome fields, but leaves `approved` and `approved_at` untouched. `review_passes` treats any retained approval as sufficient, including for a new blocking answer. The coordinator's acceptance of one set of findings is therefore applied to different findings.

**Reproduced against the real store, sequentially, with unchanged source files:**

1. Request RV-0001 and import an `issues` answer containing a medium finding.
2. Approve it with rationale `accept only the original medium issue`.
3. Import another answer into RV-0001, now with verdict `blocking` and a high finding.
4. Inspect the ticket and code coverage.

Observed:

```text
verdict = blocking
open_severity = high
approved = accept only the original medium issue
approved_at unchanged = true
review_passes(ticket) = true
code_coverage.status = covered
code_coverage.reviews = ["RV-0001 blocking, high open, approved by the coordinator"]
earlier_answers = ["DOC-0003@1"]
```

**Checks against alternative explanations:** both answers were successfully sealed, and the earlier answer was retained in history. No file-change exception, process race, old session, or old project format was involved. The live-session answer path explicitly rejects replacing an answered review at lines 402–404; the import path has no corresponding restriction. [test_agents.py:274](/home/yu/workspace/smooth-research/tests/test_agents.py:274) tests that live-review restriction. Existing import tests cover first imports, not replacement after approval.

**Impact:** current code-review coverage can incorrectly say that blocking findings were approved. The same qualification predicate is used by conclusion-review coverage, so the defect also reaches that decision path. These checks are advisory records, not a hard execution barrier; the failure is that their recorded assurance is false.

**Recommended fix:** when replacing a review answer, atomically clear its approval and approval timestamp and require a new coordinator decision. Preserve the earlier approval in audit history. If review answers are intended to be final across all entry paths, reject repeated review imports and require a recheck instead, consistently with `answer_live`.

**Focused regression:** approve a medium answer, replace it with a blocking answer, and assert that it no longer passes or supplies covered code-review status until explicitly approved again. Keep intended advisor-answer revisions working.

**F2 — P2 / medium: sibling rechecks bypass the two-review round limit**

**Location:** [reviews._round:147](/home/yu/workspace/smooth-research/src/smooth_research/reviews.py:147), especially lines 156–158; called under the request transaction at [reviews.py:498](/home/yu/workspace/smooth-research/src/smooth_research/reviews.py:498). Conclusion-review requests use the same helper.

**Problem and execution path:** the next round index is calculated from the ticket named in `--recheck-of`, without considering other tickets already in its round. After using the second slot, a caller can name the original ticket again and obtain another second slot. Explicit rechecks bypass the ordinary reuse path.

**Reproduced:** request and answer the first review with medium issues; request and answer a recheck of it; then request and answer another recheck of the first review. All source files stayed unchanged, and none of the tickets had `changed_during_review`.

| Ticket | recheck_of | round_of | round_index |
| --- | --- | --- | --- |
| RV-0001 | — | RV-0001 | 1 |
| RV-0002 | RV-0001 | RV-0001 | 2 |
| RV-0003 | RV-0001 | RV-0001 | 2 |

All three requests succeeded without a new-round rationale. Requesting a recheck of RV-0002 instead correctly raised `LIMIT`.

**Checks against alternative explanations:** the failure is fully sequential and does not depend on worker contention. The documented exception for an answer invalidated by changing files does not apply. [test_reviews.py:170](/home/yu/workspace/smooth-research/tests/test_reviews.py:170) exercises the linear chain first → second → rejected third, which explains why it misses a second child of the first ticket.

**Impact:** the documented round budget and required coordinator decision can be bypassed indefinitely. Each new ticket can initiate another model call, so this can consume additional budget without the required new-round rationale. The reproduction used manual imports and spent no model-call budget.

**Recommended fix:** enforce occupied review slots for the round root within the existing write transaction. A second recheck of an already-consumed slot must not allocate another ticket in that round. Preserve the explicit `--new-round` path and the intended replacement rule for reviews invalidated by file changes.

**Focused regression:** after two valid review slots are used, try rechecking both the latest ticket and the original root. Both must require a new round; separately retain coverage for the invalidated-answer replacement exception.

**F3 — P2 / medium: background review and advice execution silently discard `--entry`**

**Location:** [cli.py:294](/home/yu/workspace/smooth-research/src/smooth_research/cli.py:294), lines 294–297, and [cli.py:316](/home/yu/workspace/smooth-research/src/smooth_research/cli.py:316), lines 316–318. Shared launch path: [reviews._spawn:200](/home/yu/workspace/smooth-research/src/smooth_research/reviews.py:200) and `start_background` at line 210.

**Problem and execution path:** foreground handlers pass `args.entry` to `run_ticket`. Background handlers call `start_background` without it, and the detached command contains only the ticket ID and timeout. The child therefore selects the ticket's configured candidates, silently ignoring the requested override.

**Reproduced with real CLI child processes and manual entries:**

```sh
rl review run RV-0001 --background --entry manual:chosen-override
rl advise run AD-0001 --background --entry manual:chosen-override
```

The review worker log requested submission to `configured-reviewer`; the advice worker log requested submission to `configured-advisor`. Neither contained `chosen-override`. Running each same ticket in the foreground with the same `--entry` correctly requested submission to `chosen-override`.

**Checks against alternative explanations:** the manual paths keep tickets pending, allowing a direct comparison without a completed-ticket shortcut. These were actual detached CLI invocations, not a mocked argument assertion. Multiple-ticket advice deliberately rejects `--entry` at lines 313–314, but each reproduction named exactly one ticket. Background delegation has its own forwarding path, so the problem is specific to this shared review/advice launcher.

**Impact:** a single-use model/provider/effort choice is not honored. Depending on the configured candidates, a command can call a different provider or stay pending for manual submission when an automated entry was requested.

**Recommended fix:** carry the optional entry through `start_background` and `_spawn` and append it to the child command. Retain the explicit prohibition on one override for multiple advice tickets.

**Focused regression:** execute a single review and a single advice ticket in the background with an override different from their stored candidates, and assert the worker actually selects the override. A manual or fake adapter is sufficient.

**F4 — P2 / medium: advice deduplication ignores new checked literature that changes the advice package**

**Location:** [reviews._evidence_version:694](/home/yu/workspace/smooth-research/src/smooth_research/reviews.py:694), lines 694–698, and the early duplicate return at [reviews.py:720](/home/yu/workspace/smooth-research/src/smooth_research/reviews.py:720), lines 720–728. **Problem and execution path:** advice identity includes Evidence records, selected hypothesis fields, the question, target, constraints, and advisor entries. It excludes papers and their claim-assessment/locator/note links. The advice renderer includes that literature. Thus a materially different package can be classified as the same request before the new package is even generated.

**Reproduced:**

1. Prepare advice for H-0001 with question `Is our direction novel?` and import its completed answer.
2. Add a paper titled `A checked, identical prior method` and link it to H-0001 as `nearest_work`, assessment `checked`, with a section locator.

```text
duplicate = true
current advice pack contains P-0001 = true
returned ticket's sealed package contains P-0001 = false
run_ticket(AD-0001) = "AD-0001 already answered (see answer)"
```

**Checks against alternative explanations:** the relation was `nearest_work`, whose update path is fixed; this does not depend on F5. The hypothesis statement/revision, constraints, question, and advisor configuration were unchanged. The new literature was genuinely persisted and rendered. The [advice skill:3](/home/yu/workspace/smooth-research/plugin/skills/research-advise/SKILL.md:3) explicitly includes new literature changing a route's value as a consultation trigger. A live advisor can accept conversational follow-ups, but that does not refresh this completed headless ticket's sealed package. [test_reviews.py:326](/home/yu/workspace/smooth-research/tests/test_reviews.py:326) checks invalidation after new Evidence records, not changed literature.

**Impact:** the documented literature-driven advice workflow returns an obsolete consultation and offers no new call through the returned ticket. Users must alter the question or unrelated scientific records to evade reuse. This is a cache-input mismatch, separate from the declined policy about choosing historical conclusion reviews.

**Recommended fix:** derive advice identity from the same stable inputs used to construct the package, including paper data and link assessments, locators, and notes. Hashing deterministic assembled package content, together with advisor selection, would remove the parallel manually maintained definition of the inputs. Keep the existing advice budget and unchanged-request reuse behavior.

**Focused regression:** complete a consultation, add or materially update checked nearest literature, and repeat the identical question. It must prepare a package containing the new information; a subsequent unchanged repetition must deduplicate.

**F5 — P2 / medium: the literature-link fix still drops updates for `motivated_by`**

**Location:** [store.Tx.link:199](/home/yu/workspace/smooth-research/src/smooth_research/store.py:199), lines 199–201. Relation definition: [schema.py:162](/home/yu/workspace/smooth-research/src/smooth_research/schema.py:162). **Problem and execution path:** `link_paper` supports `nearest_work`, `motivated_by`, and `cites`, accepting updated assessment, locator, and note for each. The new metadata-update logic in `Tx.link` is reached only after an early return for an existing non-revision-bound relation. `motivated_by` is such a relation, so its updates still disappear.

**Reproduced using the public domain operation:**

```python

literature.link_paper(
    store, "H-0001", "P-0001", "motivated_by", "checked", locator="Section 3"

```

The second call reported:

```text
H-0001@1 motivated_by P-0001 [checked] at Section 3
```

Reading the persisted edge instead returned:

```json
{"rel":"motivated_by","id":"P-0001","label":"Paper","source_revision":1,"assessment":"search_hit"}
```

There was no locator. A successful `paper.link` event also describes the requested update, despite the unchanged relation.

**Checks against alternative explanations:** this uses an unchanged hypothesis revision, so no decision about making `motivated_by` revision-bound is needed. Its supported metadata should update on the existing edge. The fix for revision-bound `nearest_work` and `cites` is a separate branch. The new [regression test:180](/home/yu/workspace/smooth-research/tests/test_records.py:180) exercises only `nearest_work`.

**Impact:** later packages and graph readers retain an obsolete literature assessment and lose the supplied supporting locator/note, while the command and event claim success.

**Relation to the first review:** this is specifically new evidence that the fix does not cover one of the three supported paper-link relations. I am not re-reporting the repaired hypothesis-revision behavior or the repaired `nearest_work` path.

**Recommended fix:** separate identifying an existing edge from updating its metadata. For non-revision-bound paper links, update the matched edge's supplied metadata without changing its identity or creating revision-specific duplicates.

**Focused regression:** parameterize same-revision assessment/locator/note updates over all three supported paper relations. Keep revision-change assertions specific to relations that are actually revision-bound.

**Architecture quality, simplification, and test priorities**

The refactor resolves the earlier structural concern: source-level imports are acyclic, execution startup has one owner, and the contract/status consumers now share implementations. The graph plus immutable document objects is a coherent record model, and external execution remains appropriately separate from local workflow state. The tests provide useful behavioral coverage across those boundaries.

The most useful further simplifications follow directly from the findings:

- Use the actual advice-package inputs as the single definition of advice identity, removing the incomplete parallel input list.
- Centralize answer-replacement invariants in the shared answer-storage operation so manual and live paths cannot disagree about approval validity.
- Treat a review round as the unit of limit accounting; per-ticket indices alone cannot enforce an aggregate limit.
- Separate relation identity from metadata updates, instead of treating an existing non-revision-bound edge as necessarily immutable.

I found no additional obsolete compatibility layer or dead-code deletion with enough concrete benefit to warrant a finding. Restoring migrated format readers, introducing a new orchestration framework, or adding speculative worker identity machinery is not needed to address the defects above. The remaining Ruff suggestions do not justify an unrelated cleanup in this review.

The missing tests worth adding are the five focused regressions described with the findings. In particular, exercise alternatives that the current happy paths exclude: a second import after approval, a sibling recheck, an override combined with background execution, changed literature without a new Evidence node, and the non-revision-bound paper relation. This does not renew the broader test expansion declined in section 21.14.

Overall, the project is easier to understand and maintain at this HEAD, and the prior fixes substantially improve its invariants. Approval validity should be repaired before trusting the review status as an accurate account of coordinator acceptance. The four medium findings are bounded fixes to existing workflows and can be addressed without another architectural redesign.
