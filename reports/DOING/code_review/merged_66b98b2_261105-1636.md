## 分歧与处理

1. **严重度。**F2 Codex 定 P1，我定中；F6、#5、#6 Codex 定 P2/中，我定低。这几项都已修复，严重度不同不影响修复内容。
2. **Codex F1 还要求 worker 的启动失败能让调用方看到。**我没有做。根因（导入路径）已经修好；要让调用方看到启动失败，需要加一个启动握手，这是另一项功能，留给你决定要不要做。
3. **Codex F4 建议在最终写入时检查 worker 的所有权。**我只做了“已回答则拒绝”：认领（`calls` 里的 pid）已经保证不会同时有两个存活的 worker。advisor 之间的所有权竞争（C2）属于交互式会话的路径，已经修复。
4. **Claude #7 的 helper 位置。**我原本建议放在 usage，为避免循环导入改放在 adapters。Codex 无异议。
5. **Claude #2 的措辞。**Codex 指出 `decide` 不是硬门禁：它照样记录结论，同时报告缺少审查，并把它留在 attention 里。我的报告已按此更正。

## Demo 发现的问题

Demo 配置：协调者用 Opus 5.5 medium，其余角色用 `codex:gpt-6.1-terra@medium`，项目在 `~/workspace/sr-e2e/review-fix-demo`，herdr 工作区 w4。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 角色和 watcher 的标签页建到了协调者以外的工作区（w3） | `herdr tab create` 不带 `--workspace` 时，用的是 UI 当前聚焦的工作区 | `herdr.new_tab()` 带上 `--workspace $HERDR_WORKSPACE_ID`；真实 herdr 中已验证（w4:t3、w4:t4） |
| 首次分配报“delivery not confirmed” | Codex 还在显示 “Waiting for startup”（MCP 启动中），herdr 却已经报 idle；这时输入的提示只会排队 | `launch._until_started()`：等这个标记消失后再分配 |
| `rl agent reset --clear` 之后的分配丢失 | Codex v0.166 收到 `/new` 后会问 “Where should the new conversation run?”，herdr 把这个问题看成 idle；这时输入的提示只回答了问题，然后丢失 | `launch.answer_new()`：选 “Use current Git worktree”（会话自己的目录），等问题消失再返回；真实 herdr 中已验证 |
| Codex 会话没有 session id，日志读不到（model unverified、log unavailable） | 本机没装 herdr 的 Codex 集成，herdr 不上报 Codex 的 session id；rl 按设计不按目录去猜日志 | `rl agent open` 和 `rl agent list` 会说明原因，并给出 `herdr integration install codex`。没有替用户安装：安装会改动用户的 Codex 配置 |
| 装上 herdr 的 Codex 集成后，Codex 启动时先弹出 “Hooks need review” 面板，herdr 却报 idle：分配提示被面板吞掉，`rl agent answer` 也因为状态不是 blocked 而拒绝回答 | herdr 认不出 Codex 的这类对话框（hook 审核、`/new` 之后的问题） | `launch.UNSEEN`：从屏幕上认出这类对话框。`rl agent open` 不发分配，转交协调者；watcher 按“停在对话框”处理，不输入任何东西；`rl agent dialog`/`answer` 照常可用。真实 herdr 中已验证。是否信任这个 hook 由用户决定 |
| `rl report` 显示 “compute on -” | 研究员登记用量时没有填 `--hardware`，`-` 是未记录时的占位符 | 按现有设计，未改 |
