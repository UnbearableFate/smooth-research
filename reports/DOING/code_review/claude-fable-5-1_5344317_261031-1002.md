## 1. The system at HEAD 5344317, and what the five commits changed

## 2. Findings

### F1 — `rl review import` replaces an answered review, so a failing review (even one escalated to the coordinator) can be turned into a pass — **High**

**Location.** `src/smooth_research/reviews.py:377-386` (`import_answer`); the rules it bypasses are at `reviews.py:402-404` (`answer_live`: "already answered; a further review is a re-check"), `reviews.py:257-258` (`run_ticket`: "already answered"), `reviews.py:419-424` (`approve` is the coordinator's alone); the overwrite happens in `_store_answer`, `reviews.py:345-352`.

**Problem.** `import_answer` reads the ticket and calls `_store_answer` without looking at `status`. `_store_answer` then sets `status`, `verdict`, `open_severity`, `escalated`, `relation`, `observed_model` to the new answer's values and moves the old answer into `earlier_answers`. For advice tickets revisions are a feature (an advisor revises its own answer; `answer_live` checks that it is the same session). For review tickets the project's own rule, enforced in the two other answer paths, is that an answer is final and a further review is a re-check that occupies the next slot of the round. The import path has no such rule and no role check (`approve` refuses a caller with a session role; `import_answer` does not).

**Evidence** (reproduction B, appendix). With one hypothesis and experiment:

```
RV-0001 import issues/high      -> status answered, verdict issues, open_severity high, review_passes False
RV-0001 import pass             -> status answered, verdict pass,   open_severity none, review_passes True,
                                   earlier_answers ['DOC-0003@1'], round_index 1
RV-0002 (re-check of RV-0001, review 2 of the round) import issues/high
                                -> escalated True; message to the coordinator: "RV-0002: the review round RV-0001
                                   used its 2 reviews and high finding(s) remain; your decision"
RV-0002 import pass             -> escalated None, verdict pass, review_passes True
```

No test imports over an answered ticket (`tests/test_reviews.py:319,371` import once each).

**Impact.** `review_passes` is the one predicate behind the review gate: `scope.code_coverage` (what a registered run reports as "covered"), `research.review_gap` (whether a key conclusion has an independent check), the attention list and the resume pack. After the second import all of them report a passing review; the coordinator's pending decision on the escalated round becomes moot while its notice is still in the inbox. The earlier answer stays in `earlier_answers`, so the record is auditable after the fact, but nothing reads that field when deciding. In a project where the researcher is an agent, "the review failed, import a pass" is a one-command path around the gate the design calls "never a fake pass".

**Recommended fix.** Put the finality rule in one place: `_store_answer` (or a small check it calls) refuses when `t["kind"] == "review"` and `t["status"] == "answered"`, with the same message as `answer_live`, so all three paths agree. Keep advice revisions. If re-importing a review must stay possible to correct a wrong file, make it explicit and coordinator-only (`--replace --reason ..`, refused when `caller_role()` is set, recorded as a `review.replaced` event) and let `_round` treat the replaced answer like a changed-during-review one. Add the test: import over an answered review raises CONFLICT; import over an answered advice ticket keeps the earlier answer.

### F2 — `prepare_advice` is two writes around a file write; a failure between them leaves a round that cannot be re-prepared, cannot be run, cannot be cancelled, and counts toward `advice.max_rounds` — **Medium** (new evidence for the 21.13 item "ticket and package created atomically")

**Location.** `src/smooth_research/reviews.py:730-755` (first write creates the tickets at 730-745; package file and sealing at 746-748; second write sets `request_ref` at 749-755); the dedupe check at `reviews.py:723-728` matches tickets of any status; `advice_rounds` counts pending tickets, `reviews.py:701-707`; `run_ticket` refuses a ticket without `request_ref` with "prepare it again", `reviews.py:247-248`; `agents.brief` reads `t["request_ref"]` unguarded, `agents.py:331`; `cli.main` catches only `RLError`, `cli.py:840`.

**What 21.13 recorded** (design document line 1427): a ticket without a package is left only when writing the package itself fails (disk, permission); `rl review run` tells the user to prepare it again; changing the order of the three request functions brings little. The recovery it relies on does not exist for advice tickets, and the failure window is not only the file write: it also contains the second `store.write()`, which can time out on the write lock (60 s) or be interrupted (Ctrl-C, the host killing a tool call), and the sealing step `documents.prepare`.

**Evidence** (reproduction A, appendix; `documents.prepare` made to raise for the advice package):

```
prepare_advice raised: OSError disk full while sealing the package
tickets: [('AD-0001', 'pending', None, 1), ('AD-0002', 'pending', None, 1)]     <- no request_ref
advice_rounds counts: [1]                                                        <- the round is used
prepare again -> "AD-0001, AD-0002 already ask this with the same evidence (pending, pending);
                  send only new data, or wait for new evidence"                   <- dedupe refuses
run_ticket   -> INVALID "AD-0001 has no request package; prepare it again"       <- circular
different question -> "advice round 2 (2 of 3 used)"                             <- the broken round counts
any cancel/withdraw command for a ticket? []
rl agent brief adv (the ticket assigned to a live advisor) -> KeyError: 'request_ref'  (traceback, not an rl error)
```

The same two-write shape is in `request_review` (`reviews.py:490-520`) and `request_conclusion_review` (`reviews.py:597-615`). There a second request works, because `_reuse` only reuses answered passing tickets, but the broken ticket stays `pending` forever: it is listed among the open tickets in `rl status`, and when a researcher session requested it, `watch.assignment_state` (`watch.py:128-132`) keeps that session "waiting for review RV-x" with the problem "RV-x has no reviewer session" in every round, so the watcher never reminds that session when it is idle.

**Impact.** One lost round of a budget of three, the same question blocked until the evidence version changes, a coordinator assignment that crashes the agent's briefing, and no command to clear any of it (a manual database edit is the only way). Low probability per call, no recovery path once it happens.

**Recommended fix.** Make a ticket and its package one write. All three functions can compute the package text before the write (the review package needs the ticket id: take it from `tx.next_id` inside the write, write the file, `documents.prepare` it, `documents.register`, then `tx.create` the ticket with `request_ref` set, all inside the one `with store.write()`; a file left behind by a failed transaction is harmless). Doing it in one helper also removes the triplicated shape (§6) and closes the cross-process race in `prepare_advice`, whose dedupe check runs in a read transaction before the write. Minimal alternative: exclude tickets without `request_ref` from the dedupe match and from `advice_rounds`, and guard `agents.brief`. Either way a `rl review|advise cancel AD-x --reason ..` for pending tickets would give the coordinator the general remedy that is missing today.

### F3 — Usage revisions are numbered wrong from the third one on — **Low**

**Location.** `src/smooth_research/runs.py:442` and `:456` (`_usage`).

**Problem.** `current` holds only the non-superseded records of the accounting reference, which is at most one after the first revision, so `"revision": len(current) + 1` is 2 for every later revision.

**Evidence** (reproduction C): three `add_usage` calls on `miyabi-pbs:1.opbs` (the third two with `revise=True`) record `U-0001` revision 1, `U-0002` revision 2, `U-0003` revision 2. The `supersedes` edges are right (`U-0003 -> U-0002`), so nothing else misreads the chain; the field itself is wrong in a system whose purpose is accurate records. `tests/test_runs.py:207` revises once, which is why the suite does not see it.

**Recommended fix.** `"revision": old["revision"] + 1 if current else 1`. One assertion on a third revision.

### F4 — `rl run register --run` writes a sealed object for a contract draft it does not register — **Low**

**Location.** `src/smooth_research/runs.py:63` (`prepare_contract` for every registration) versus `:82` (`seal_contract` only for a new run).

**Problem.** `prepare_contract` calls `documents.prepare`, which writes the content-addressed object file under `research/objects` (mode 0o444; the directory is kept in git by design). For an attempt of an existing run the sealed revision is never registered, so a changed draft leaves an object file no `DocRevision` names.

**Evidence** (reproduction D): after editing the draft and registering a second attempt with `--run`, one new file appears in `research/objects` and no `DocRevision` refers to it; `E-0001.contract_ref` stays `DOC-0002@1` (correct: an attempt of a run belongs to the run's sealed revision).

**Recommended fix.** Call `prepare_contract` inside the new-run branch only (the digest comparison in `seal_contract` needs the prepared object, so prepare there), or have `documents.prepare` compute the digest first and write the object only when a registration follows. Optional: when the draft differs from the run's sealed revision, say so in the summary of `register --run`; the silent acceptance is correct but easy to misread as "the run uses the edited contract".

## 3. Candidates examined and not reported

Each of these was traced to its callers and tests and either disproved or judged below the bar.

- **A reviewer session reminded while a headless worker holds its ticket.** `OPEN_TICKET` includes `running` (`watch.py:37`), so a reviewer session assigned `RV-x` is told to continue when someone runs `rl review run RV-x` in parallel. Needs mixed use of the two paths for one ticket; the cost is one superfluous reminder. Not reported.
- **A removed requester worktree makes every reviewed path "changed".** `scope.changed_since_request` counts an unreadable path as changed, so an answer given after `rl agent close --remove-worktree` never counts. Defensible: the reviewer could not have read the files either.
- **Non-`RLError` exceptions in `open_session`/`start_agent` or `watch.run`.** `herdr.call` converts every failure (timeout, OSError, bad JSON, non-zero exit) into `RLError`; `store.write` converts the lock error. I found no concrete source of another exception type on those paths.
- **Pid reuse in `_worker`.** Handled by the `/proc/<pid>/cmdline` check; a reused pid that cannot be read is treated as alive, which errs on the safe side.
- **Headless Codex advisors cannot search the web.** `codex exec --help` on the installed Codex lists no `--search` (only the interactive `codex` does), so `adapters.call_codex` correctly ignores `web`; the herdr advisor gets `--search` (`launch.py:41`). A capability difference, documented in the adapters docstring (`adapters.py:293`), not a bug.
- **Nested transactions, `message_seq` versus `data_version`, config digests with non-string keys, `_accept_global_options_everywhere`, `label_of` for caller-chosen ids, export/restore**: examined again at this HEAD; behaviour is correct.
- **Items decided in 21.13/21.14** (not re-reported): the `register` request-idempotency design, the executor-namespace warning, the advice-round accounting of unanswered rounds, keeping `params` out of `_mismatches`, the watcher's reminder limits, the plugin build. F2 is the only item re-raised, and only because the recorded rationale assumes a recovery path that the advice side does not have.

## 6. Architecture quality, simplification and deletion

**Quality.** Clearly better than at 92513a6. The split into `scope`, `messages`, `worktrees`, `launch` gives each concern one owner and removed the three import cycles; `start_agent` makes `rl agent open` and the watcher's restart one code path, which is exactly where the two had drifted before. State ownership is clear: records in the graph, documents as sealed objects, the process claim on a ticket as the last `calls` entry, the watcher's memo in `Session.watch`. The invariants that matter (one writer at a time, idempotent requests, a review passes only without medium findings or with approval, an advice round is counted when prepared) are each enforced in one place, with the one exception F1 names. Tests run the real CLI in-process with fake hosts and a fake herdr, which is the right level.

**Simplify / delete.**

- The three ticket-creating functions (`request_review` 490-520, `request_conclusion_review` 597-615, `prepare_advice` 730-755) repeat the same create→write package→seal→register→update shape. One helper that takes the package text and the ticket fields, in one write transaction, deletes about 40 lines and fixes F2.
- The "already answered" rule lives in `run_ticket` and `answer_live` and is absent from `import_answer`; moving it into `_store_answer` makes one source of truth (F1).
- `reviews.py` (760 lines) is the largest module after `cli.py`; the advice part (`reviews.py:690-760`, with `advice_pack` in `context.py`) could become `advice.py` now that `scope.py` holds the code-review scope logic. Optional.
- `launch.excerpt`'s unused `lines` parameter can go.
- Nothing else looks like legacy or compatibility code; b1aaaad removed what was left.

## 7. Verdict

The project is sound and in better shape than at the previous review: the earlier findings are fixed, the refactor dropped no behaviour, the module graph is acyclic, and the suite passes. Two findings deserve a fix before the review gate is relied on in a multi-agent project: F1 (High), because it is a one-command path that turns a failed or escalated review into a pass without the coordinator; and F2 (Medium), because the failure leaves state nobody can repair with `rl`. Both fixes are small and the second also deletes duplication. F3 and F4 are record-accuracy details. No architectural rework is needed.
