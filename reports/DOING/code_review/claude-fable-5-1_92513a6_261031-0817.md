## 1. How the system is built

**Layers.** One embedded LatticeDB graph per research project (`research/state/research.lattice`) behind a single `Store` (`store.py`). Every write is one process-exclusive `flock` plus one database transaction that bumps `Meta.data_version`; reads take a shared `flock`. Twenty entity types and twenty-three relations are declared once in `schema.py` and enforced at the `Tx` boundary (required fields, enums, label pairs, acyclicity, revision-bound edges). Documents are content-addressed, sealed objects written atomically *before* the transaction that registers them (`documents.py`), so a crash leaves at most an unregistered object, which `rl doctor` reports.

**Records.** `research.py` (hypotheses, experiments, evidence, decisions, links, attention items), `runs.py` (immutable RunSpec, attempts, observations with a state-projection function, results, usage), `tasks.py` (sessions, messages with a per-role cursor, task ownership), `reviews.py` (review and advice tickets, review rounds, scope fingerprints, code-coverage check, conclusion packages, advice rounds), `literature.py`.

**Execution and agents.** `adapters.py` runs headless `claude -p` / `codex exec` / `pi -p` calls; `delegate.py` runs a headless researcher; `agents.py` + `herdr.py` open interactive sessions in herdr tabs, each researcher in its own git worktree and branch; `watch.py` is a loop in its own tab that restarts gone agents and reminds idle ones.

**Projections.** `context.py` (work/resume/advice packs with a token budget), `view.py` (tree, mermaid, HTML page, stage report), `manuscript.py` (Markdown or LaTeX draft with refreshable record blocks), `snapshot.py` (export/restore/doctor), `hooks.py` (session-start note), `cli.py` (one argparse entry point; only `RLError` is turned into `error[CODE]`).

**Invariants the code actually enforces (and tests):** one claimant wins a task (4-process fork test); same request id is idempotent and conflicts on new content; RunSpecs refuse mutable code versions; an older observation never overrides a recorded end; contradicting ends mark the attempt for checking; a killed writer leaves a consistent store (SIGKILL test); the sealed contract does not change when the draft is edited; a hypothesis revision keeps old evidence on the old revision; review rounds hold two reviews then escalate; an answer given while the files changed does not count; a run records whether reviews still cover its code; nothing in the configuration stops a command.

**Verified against the installed hosts.** Every flag the adapters and `launch_args` pass exists in the installed CLIs: `claude` (`--safe-mode`, `--restricted`, `--strict-mcp-config`, `--tools`, `--permission-mode` with `auto`/`dontAsk`, `--allowedTools`, `--disallowedTools`, `--add-dir`, `--effort`, `--session-id`, `-n`), `codex exec` (`--json`, `--skip-git-repo-check`, `--model`, `--cd`, `-c`, `--output-last-message`, `--sandbox`), `pi` (`--mode json`, `--model`, `--session-id`, `--name`, `--thinking`, `--tools`), and `herdr` (`tab create --cwd --label --env --no-focus`, `tab get/close`, `pane get/run`, `agent start --kind --pane --timeout --`, `agent prompt --wait --timeout` with the `agent_blocked` / `agent_prompt_stalled` codes the wrapper relies on, `agent read --source visible`, `agent send-keys`, `agent get`). The test fakes accept any argv, so this was not previously checked anywhere.

## 2. Findings

### F1. High: a YAML config with a date (or any non-JSON scalar) crashes review request, answer storage and run registration

- **Location:** `src/smooth_research/reviews.py:480-485` (`_config_digest`); reached from `fingerprint` (`reviews.py:505`), `_changed_since_request` (`reviews.py:316`, called by `_store_answer` at `reviews.py:346`) and `code_coverage` (`reviews.py:706-723`).
- **Problem:** `_config_digest` parses a config with `yaml.safe_load` and hashes it through `digest_json` → `json.dumps(sort_keys=True)` with no `default`. YAML implicitly types `2026-10-30` as `datetime.date` (also timestamps, `!!binary`), which `json.dumps` cannot serialize. The function only catches `(ValueError, yaml.YAMLError)`, so the `TypeError` escapes. None of the three callers catches it either: `code_coverage` catches only `(OSError, subprocess.SubprocessError)`, and `cli.main` converts only `RLError`.
- **Evidence (reproduced in a scratch project):**
  - `reviews.request_review(..., configs=["configs/run.yaml"])` with `data_snapshot: 2026-10-01` in the file → `TypeError: Object of type date is not JSON serializable`, traceback, no ticket.
  - A review requested with a plain config, the config later gains `run_date: 2026-10-30`, then `rl review run RV-0001`: the fake Codex answers (call log `research/calls/RV-0001.codex.1.log` written), then `_store_answer` → `_changed_since_request` raises. Ticket stays `pending`, `answer_ref` is `None`: **the model's answer is lost after the call was paid for**. With `--background` the ticket is left `running` with a dead worker, and `rl review run` again repeats the call and the crash.
  - After a passing review whose scope has that config, `rl run register` for the experiment → `code_coverage` raises the same `TypeError`: no run can be registered for that experiment until the file is changed.
- **Impact:** Loss of review answers, a stuck ticket, and run registration blocked, triggered by ordinary config content (dates are common in ML configs: data snapshots, run dates). Every failure is a Python traceback to an agent that cannot act on it.
- **Fix:** Make `_config_digest` total: `json.dumps(..., default=str)` (or normalize dates/bytes before digesting) and catch `TypeError` alongside the others, falling back to the byte digest. Independently, make the two downstream sites safe: `code_coverage` should return `{"status": "unchecked", "reason": ...}` on *any* exception while digesting, and `_store_answer` must never fail after the answer text exists (treat a digest failure as `changed`, or write the answer first and compute `changed_during_review` in a guarded step). Add a test with a config containing a date, a timestamp and an integer key.

### F2. Medium: task owner updates are accepted from any role, not only the owner

- **Location:** `src/smooth_research/tasks.py:167-175` (`_owner_write`), used by `progress` (`tasks.py:178`, i.e. `rl task deliver|wait|block|resume`) and `handoff` (`tasks.py:212`).
- **Problem:** The gate is `if not task.get("owner_role")`. It checks that *some* owner exists, never that `from_role` is that owner. The docstring ("only a claimed task takes owner updates") and the design ("exactly one claimant wins") imply owner-only updates, and the two other places that touch ownership do enforce it (`agents.assign` at `agents.py:411`, `delegate.delegate` at `delegate.py:120-123`).
- **Evidence (reproduced):** `tasks.claim(store, "T-0001", "researcher-1")`, then `tasks.progress(store, "T-0001", "delivered", "researcher-2", "done by someone else")` succeeds. The task is `delivered` with `owner_role` still `researcher-1`, and the coordinator's inbox shows `MSG-0002 RESULT from researcher-2 task T-0001`. The same holds for `wait`, `block`, `resume` and `handoff` (which releases the task to `ready`). `rl task accept` then accepts it.
- **Impact:** The ownership invariant that the whole task protocol, the watcher (`_assignment` keys on `Session.assignment` + task state) and the coordinator rely on is only advisory. An agent session that passes the wrong `--role` (a common LLM slip: these sessions are told their name only through an environment variable) can deliver, block or hand off another session's task, and the record attributes it to the wrong role. `test_handoff_releases_the_task_for_the_next_owner` only checks the *no owner* case.
- **Fix:** In `_owner_write`, pass `from_role` and raise `CONFLICT` when `task["owner_role"] != from_role` (message: who owns it, and that the owner continues with `task resume`). Default `--role` to `SMOOTH_RESEARCH_ROLE` when set, so sessions opened by `rl agent open` cannot name another role by accident. Add a test for a non-owner `deliver` and `handoff`.

### F3. Low: `rl run record --exec-id` without `--exec-namespace` raises `AttributeError` instead of the intended `INVALID`

- **Location:** `src/smooth_research/runs.py:273-276`; the CLI builds the ref at `cli.py:247-249` with `executor_namespace: args.exec_namespace` (possibly `None`).
- **Problem:** The bare-PID warning does `ref.get("executor_namespace", "").count(":")`. The key is present with value `None`, so `.get` returns `None` and `.count` fails. The proper validation (`_bind`: "execution_ref needs executor_namespace") runs later, inside the transaction, and is never reached.
- **Evidence (reproduced):** `rl run record --attempt ATT-0001-1 --source shell --state running --exec-id 12345` → `AttributeError: 'NoneType' object has no attribute 'count'`.
- **Impact:** The most likely mistake in the most frequently typed command gives a traceback instead of the one-line correction the error path was written to give.
- **Fix:** `(ref.get("executor_namespace") or "")`, or validate the ref's required keys (reuse the loop in `_bind`) before the warning. One CLI test.

### F4. Low: `ended_at` of a session is the previous write's timestamp, not the end time

- **Location:** `src/smooth_research/tasks.py:51` (`end_session`) and `tasks.py:38` (`start_session`, superseding the earlier coordinator).
- **Problem:** Both write `"ended_at": tx.meta()["updated_at"]`, which is the time of the *last committed write*, read at the start of this transaction. `agents._end` (`agents.py:395`) correctly uses `now_utc()`.
- **Evidence (reproduced):** start a session, sleep 2.5 s, `end_session`: `created_at 08:15:05`, `ended_at 08:15:05`, `updated_at 08:15:07`. In a quiet project `ended_at` can precede the real end by hours.
- **Impact:** Wrong session durations in `rl agent list --all`, reports and exports; inconsistent with the other end path.
- **Fix:** Use `now_utc()` in both places.

### F5. Low: a ticket already running in a background worker can be run again

- **Location:** `src/smooth_research/reviews.py:244` (`run_ticket` returns early only when `status == "answered"`); `_worker_alive` at `reviews.py:187` is consulted only by `show` (`reviews.py:457`).
- **Evidence (reproduced):** a ticket set to `running` with a live worker PID; `run_ticket` proceeds and calls the model again (`second run proceeded: pass`).
- **Impact:** Duplicate paid model calls when an agent re-runs a ticket it started with `--background` (the summary of `start_background` tells it to check with `show`, but nothing stops the re-run); two writers of the same ticket's `calls`.
- **Fix:** In `run_ticket`, if `status == "running"` and `_worker_alive(t)`, raise `CONFLICT` ("worker pid N is running; `rl review show RV-x`"), with the existing "run again" path kept for a dead worker.

### F6. Low: ticket creation is not atomic with its package; a failed package write leaves phantom tickets (and, for advice, consumes a round)

- **Location:** `src/smooth_research/reviews.py:547-577` (`request_review`), `758-777` (`request_conclusion_review`), `891-916` (`prepare_advice`).
- **Problem:** Each does: write 1 creates the ticket(s) as `pending`; then writes the package file(s) under `research/packages/`; then write 2 sets `request_ref`. A failure in between (disk, permissions, an exception in `_review_package`) leaves tickets without a package. `run_ticket` then says "prepare it again", but a repeat request creates *new* tickets (reuse only matches answered ones), and `advice_rounds` counts the phantom round as `pending`, so the user hits `LIMIT` one round early.
- **Fix:** Follow the pattern `documents.prepare` already uses: write the package first under a name that does not need the id (or reserve the id and write both the ticket and `request_ref` in one transaction after the file exists), so the only possible leftover is an unreferenced file. For advice, exclude tickets without `request_ref` from `advice_rounds`.

### F7. Low (complexity): compatibility paths for record and config formats that existed for less than two days

- **Location:** `src/smooth_research/project.py:28-32, 55-69, 140-149, 189-199, 209-216, 254-268` (earlier plan/constraints paths, retired keys, moved directories, `inherit`/`candidates`/`primary` model forms); `research.py:325-329` (`review_passes`: "answered before severities were recorded"); `runs.py:116-120` (`code_review_note(None)`: "registered before the check existed"); `reviews.py:862-868` (`advice_rounds`: "tickets from before rounds existed"); `reviews.py:697-701` (`code_coverage`: reviews that "recorded no scope"); plus the tests that exercise them (`test_records.py:267-385`, `test_reviews.py:510-516`).
- **Evidence:** The repository's first commit is 2026-10-30 07:13; the layout, model-list and review-round changes these shims cover landed 2026-10-31 02:01–06:22. Version is `0.1.0`, unpublished.
- **Impact:** About 150 lines of branching in the config loader and three record-interpretation functions, each a second way a record can mean "pass"/"covered"/"a round", for data that only the author's own test projects can hold. They also weaken invariants: a ticket with no `open_severity` passes on `verdict in (pass, issues)` even if medium findings existed in its text.
- **Fix:** Before any external user exists, migrate the few existing projects once (a short script or `rl doctor --migrate` that renames `docs/plan/original.md`, rewrites the model lists and sets `open_severity` from the stored answers) and delete the shims; keep only a plain error for unknown config keys. If the author wants to keep the warnings, keep `RETIRED_KEYS` and drop the alternate readers.

### F8. Low (architecture): module cycles hidden by function-level imports; ownership of a few concerns is split

- **Location:** `runs.py:60` (`from .reviews import code_coverage` inside `register`), `tasks.py:246` (`from .agents import branch_status`), `agents.py:261, 376, 500` (`watch`), `reviews.py:174, 178, 369, 443` (`agents.assign`, `tasks._message`), `snapshot.py:86` (`context.resume_pack`).
- **Problem:** Three real cycles (runs↔reviews, tasks↔agents, agents↔watch) are broken by local imports with comments explaining the cycle. They follow from concerns living in the wrong module: `code_coverage` / `_code_reader` / `_code_reviews` / `fingerprint` / `_config_digest` (what a *run* executes vs. what a review saw) sit in `reviews.py` (921 lines, the largest module, which also holds advice rounds and conclusion packages); `_message` (tasks) is the write primitive for reviews, agents and watch; `watch._restart` (`watch.py:175-231`) re-implements the tab → `agent start` → trust-question → record sequence of `agents.open_session` (`agents.py:198-268`) with its own error handling.
- **Impact:** Harder to reason about which module owns the review-coverage rule and the launch sequence; any fix to launching (F-none today, but e.g. the trust-question handling changed twice in the last day) must be made in two places.
- **Fix:** Extract `scope.py` (fingerprint, config digest, code reader, coverage check) imported by `runs` and `reviews`; `messages.py` (`_message`, `notify`) imported by everyone; move the launch sequence into one `agents._launch(store, session, pane, timeout)` used by `open_session` and `watch._restart`. Then the local imports can go.

Write only on change.

## 3. Candidate findings that did not survive verification

Listed so they are not re-raised:

- **Nested store locks** (a `store.write()` inside a `store.read()` would spin 60 s and raise `LOCKED`, since each `_lock` opens a new descriptor): traced every caller in `agents`, `watch`, `reviews`, `tasks`, `runs`, `context`, `manuscript`, `view`, `hooks`; all transactions are closed before the next opens, and model calls, herdr calls and git run outside transactions.
- **`message_seq` inside one transaction:** `tx.meta()` (a Cypher query) does see uncommitted `set_property`; two `_message` calls in one write get seq 1 and 2 (reproduced). No caller creates two anyway.
- **Review-round accounting** (`_round`, `changed_during_review` taking the place of an answer, `LIMIT`, `--new-round`): traced and covered by `test_a_review_round_holds_two_reviews_and_then_goes_to_the_coordinator` and `test_an_answer_given_while_the_files_changed_does_not_count`.
- **Scope paths across worktrees:** `fingerprint` records paths relative to the requester's checkout and `code_coverage` reads them relative to the registering caller's checkout or from the named commit; consistent after a merge, as intended.
- **`_config_digest` on non-YAML configs (`.py`, `.toml`):** YAML parses them as scalars or fails; the digest still changes with any edit, only `--ignore-keys` has no effect. Not a bug, worth one sentence in the skill.
- **Headless Codex reviewers with write access:** `call_codex` passes `-c approval_policy="never"` and no sandbox for reviewers since 92513a6, so read-only is enforced only by the prompt. This is a deliberate, documented trade-off (`docs/configuration.md` §1 模型, commit message); listed here as an accepted risk, not a finding.
- **`Session.assignment` vs `Task.owner_role` as two sources of "who works on T-x":** by design the coordinator assigns and the session claims; `assign` refuses a task owned by another role, so they cannot diverge in the dangerous direction. F2 is the gap that lets them diverge.

## 5. Test coverage gaps that matter

The suite is unusually strong on invariants (real fork concurrency, SIGKILL, idempotency, the miyabi-mcp export fixtures, fake host CLIs and a fake herdr). What it does not cover:

1. **Owner-only task updates** (F2): no test that a non-owner `deliver`/`handoff` is refused.
2. **Config digests with YAML-typed scalars** (F1): no test with a date, timestamp, binary or integer-keyed config; no test that `_store_answer` survives a digest failure.
3. **Background workers:** `reviews.start_background`, `_spawn`, `_worker_alive`, `run_many(background=True)` and `delegate.start_background` have no tests at all (grep for `background` in `tests/` finds nothing); PID bookkeeping, log files and the "worker not running" hint are unverified.
4. **Host CLI flag drift:** the fakes accept any argv. A test that, when the real `claude`/`codex`/`pi`/`herdr` are on PATH, asserts the flags in `adapters.py`, `agents.launch_args` and `herdr.py` appear in `--help` (skipped otherwise) would have caught any of the unusual flags (`--safe-mode`, `--restricted`, `agent prompt --wait`) silently changing.
5. **CLI edge inputs:** F3 (`--exec-id` alone), `rl run record` with a batch item lacking `attempt_id` and no `--attempt`, `--param` with invalid JSON values.
6. **Literature:** only `normalize` is tested; `fetch_metadata`, `search`, `add_paper --fetch`, `link_paper`, `set_access` can be tested by monkeypatching `_get`.
7. **Untested commands:** `rl view`, `rl graph --mermaid`, `rl history`, `rl digest`, `rl show DOC-x`, `rl agent reset --compact` (the 10-minute `--wait` path), `rl session end`.
8. **Store failure paths:** `LOCKED` after `LOCK_TIMEOUT_S`, `_open` retry on `LatticeDatabaseLockedError`, unsupported `schema_version`.
9. **Watcher branches:** `_restart` when the pane still holds an unnamed agent (`watch.py:190-193`), `_answer_trust` timeout and `gone` branches, `MAX_RESTARTS` is tested but the hour window expiry is not.
10. **Sealed documents from flags:** `hypothesis revise --statement-file`, `decide --rationale-file`, `msg --doc`.

## 6. Architecture quality, simplification and deletion opportunities

**Quality.** For a two-day-old codebase this is a well-structured system: a single write path with real atomicity and crash tests, a declarative schema, content-addressed documents, idempotent request keys, honest "unknown/unverified/not a pass" semantics everywhere, and configuration that warns instead of failing. Error messages tell the agent the next command. The herdr and host integrations match the installed binaries. The main weakness is at the input boundary: anything that is not an `RLError` becomes a traceback (F1, F3), and one protocol invariant is documented but not enforced (F2).

**Simplify or delete.**

- Drop the pre-release compatibility readers once existing projects are migrated (F7): ~150 lines and three alternate interpretations of records.
- Extract `scope.py` and `messages.py`, unify the session launch sequence (F8): removes the cycles and `watch._restart`'s copy of `open_session`.
- Merge the two `_contract` helpers and the three contract-field tuples; one `SEVERITIES` (F9).
- Delete `Tx.unlink`, `__init__.main`, `RLError.as_dict`; import `LatticeDatabaseLockedError` from the public module.
- Consider a catch-all in `cli.main` that turns any unexpected exception into `error[INTERNAL]: <type>: <message>` with the traceback appended to `research/calls/rl-errors.log`; the two crashes found here would then at least leave the agent with an actionable line and the record consistent.
- `hooks.session_start` recomputes the coordinator/open-tasks/attention summary that `research.status` and `context.resume_pack` also compute; one `summary(tx)` helper would serve all three.
- `agents.answer` and `watch._round` both decide what to do with an idle session after a dialog; the branch in `answer` (`agents.py:375-381`) could call the watcher's reminder path instead of re-implementing the prompt.

## 7. Verdict

**Solid foundation, not yet safe for a real project until F1–F3 are fixed.** The records core (store, documents, runs, reviews rounds, tasks) is correct in the paths that matter and is protected by meaningful tests. F1 can lose a paid review answer and block run registration on ordinary config content; F2 lets any session act as any task owner; F3 turns the most common operator slip into a traceback. All three are small, local fixes with obvious tests. After that, the next investment is structural rather than corrective: remove the compatibility shims while they are still cheap to remove, untangle the three module cycles, and add the background-worker and host-flag tests.
