## Architecture and ownership

The project is a local research ledger with agent orchestration around it:

1. The argparse CLI and host hooks dispatch to domain functions. Shared skills, the `rl` shell launcher, and host substitutions are assembled into Claude/Codex plugin packages by `scripts/build_plugins.py`. This is a useful single source for the two distributions.
2. `project.py` separates the authoritative project directory from a researcher's Git checkout. Records live under the main project's `research/`; code inspection and review fingerprints can refer to an individual worktree. Configuration has documented defaults, warnings, and a last-readable cache.
3. `schema.py` and `store.py` wrap the pinned LatticeDB dependency. Shared/exclusive file locks cover database access; write transactions own IDs, events, request deduplication, and graph changes. `documents.py` seals content before registering its reference, using BLAKE2b objects and atomic durable writes. Interrupted preparation can leave an unregistered object without exposing a half-registered document.
4. `research.py` owns hypotheses, experiment contracts, evidence, and decisions. `runs.py` owns immutable RunSpecs, attempts, execution references, imported observations/results, and accounting. Execution state, result completeness, evidence validity, and scientific support are deliberately distinct. The CLI records external execution; it does not submit or cancel experiments.
5. `tasks.py` owns task claims, progress, messages, and inbox cursors. `agents.py`, `delegate.py`, and `watch.py` bridge these records to subprocesses, herdr sessions, Git worktrees, and recovery/reminder behavior. This boundary has several independently mutable copies of ownership: task owner, task branch, session assignment/branch, and ticket worker state.
6. `reviews.py` builds sealed requests, selects model adapters, records answers, and provides review coverage. `context.py`, `view.py`, and `manuscript.py` produce projections; reports, manuscript tables, and conclusion-review tables share `arm_rows`. Sharing that computation is sound, but F1 shows that a shared semantic error propagates widely.

The important architectural distinction is between **a transaction that safely commits records** and **a workflow that safely owns an operation across transactions and external effects**. The former is reasonably well implemented. F3, F4, and F6 arise in the latter. Repairing those boundaries does not require replacing LatticeDB or introducing a distributed service.

## Findings

### F1 — P1: A late partial result replaces complete metrics in every shared result table

**Location:** [view.py:128](/home/yu/workspace/smooth-research/src/smooth_research/view.py:128), especially lines 128–137.

**Problem and execution path:** `runs.import_result` retains result revisions and sets the attempt's aggregate status through `runs._best` (lines 360–363, 396), which gives complete results precedence. `view.arm_rows` instead filters out rejected revisions and takes `results[-1]` without considering completeness. Its metrics flow into `view.report`, `manuscript.blocks` at line 220, and `reviews._conclusion_body` through `_arm_table`.

**Observed evidence:** On one successful attempt, import a complete result with `acc=0.9`, then a partial result with `acc=0.1`. The attempt remains `result_status="complete"`, but its row becomes:

```text
arm=wd, seeds=0, attempts=1 ended/success, acc=0.1 (n=1)
```

The generated report, manuscript, and sealed conclusion-review package all contained `0.1 (n=1)`.

**Disproof checks:** The late partial is allowed input and is not rejected or unusable. This is not an objection to displaying partial results when no complete result exists. The documented contract explicitly says partial results never replace complete ones (`plugin/skills/smooth-research/references/workflow.md:129`). `tests/test_runs.py:134–160` already exercises this sequence, but line 149 checks only the attempt status. The numerical consumers are not asserted.

**Impact:** A delayed intermediate upload silently changes the reported experimental outcome while the surrounding record still appears complete. Reviewers and manuscript readers receive the wrong measurement.

**Recommended fix:** Define one effective-result selector: latest non-rejected complete revision when present, otherwise latest non-rejected partial revision; apply usability checks to the selected revision. Use it consistently for status/projections. Retain all historical revisions.

**Regression test:** Assert the actual table, manuscript, and review-package values after complete → partial, then after rejecting the complete revision. Also cover a later complete correction.

### F2 — P1: An explicitly wrong arm or seed is still accepted as a planned comparison

**Location:** [runs.py:25](/home/yu/workspace/smooth-research/src/smooth_research/runs.py:25), consumed by `_mismatches` at lines 342–357 and `import_result` at lines 387–395.

**Problem and execution path:** `COMPARED` excludes `arm`, `seed`, `replicate`, and `params`, although they are RunSpec fields defining scientific identity. An optional absent `spec_digest` therefore permits a manifest to explicitly contradict these fields while receiving `spec_match=True` and `usable_for_planned_comparison=True`. `view.arm_rows` groups that measurement under the registered RunSpec's arm/seed. `research.add_evidence` relies on the usability flag for its confirmatory-evidence guard.

**Observed evidence:** Register arm `wd`, seed `0`; finish its attempt successfully; import:

```json
{"status":"complete","arm":"control","seed":99,"metrics":{"acc":0.9}}
```

The result was marked matching and usable, the table displayed `wd | 0 | ... | 0.9 (n=1)`, and creating valid confirmatory evidence from it succeeded.

**Disproof checks:** A supplied mismatching whole-spec digest would catch this, but that digest is explicitly optional. The importer accepts these manifest fields and preserves them. This finding concerns explicit contradictions, not absent or unknown provenance. Retry registration already treats a changed scientific spec as a different run (`runs.py:74–77`), so silently accepting the contradictory result undermines an otherwise enforced distinction.

**Impact:** A control result, another seed, or another parameterization can be attributed to the intended treatment and used as confirmatory evidence.

**Recommended fix:** Compare every supplied, known scientific-identity field against its RunSpec, including arm/seed/replicate/params and other execution-defining fields. Keep the documented treatment of omitted/unknown values. A contradiction must make the result unusable for the planned comparison while preserving the raw manifest.

**Regression test:** Explicit arm, seed `0`, replicate, and parameter mismatches must be retained but excluded from comparison tables and refused for confirmatory evidence. Include omitted fields as a separate accepted/unverified case.

### F3 — P1: Owner updates neither verify the owner nor respect terminal task states

**Location:** [tasks.py:167](/home/yu/workspace/smooth-research/src/smooth_research/tasks.py:167), especially lines 171–175; writes occur in `progress` at lines 187–198 and `handoff` at lines 214–216.

**Problem and execution path:** `claim` correctly serializes the initial winner. Subsequent `_owner_write` calls only check that *some* owner exists. They do not compare `from_role` with `owner_role`, fence the owner session/revision, or check whether the current task state permits the update. Coordinator stop/accept preserves the owner. The public CLI forwards the role directly to these functions (`cli.py:145–166`).

**Observed evidence:** All three sequences succeeded against the real store:

- Alice claims → coordinator stops → Alice's late delivery changes `stopped` to `delivered`.
- Coordinator accepts → a different role resumes → `accepted` becomes `active`, still owned by Alice.
- Alice hands off → Bob claims → Alice's delayed delivery is accepted; owner remains Bob but the RESULT message is from Alice.

**Disproof checks:** The exclusive write lock prevents simultaneous database writes but does not reject a stale logical writer. The role argument is not validated by the CLI. `tests/test_records.py:31` tests concurrent initial claims; the handoff test at line 48 rejects old-owner writes only during the unclaimed interval, then exercises only the new owner.

**Impact:** Delayed subprocesses or sessions can undo coordinator decisions, deliver another owner's task, or release its ownership. Recovery and handoff cannot rely on the stored state even when all workers use the public API.

**Recommended fix:** Validate the current owner identity and permitted source state inside the same write transaction as the mutation. Use the stored session/revision to reject stale claims where sessions are known. Preserve the explicit coordinator reopen operation; owner progress must not implicitly reopen accepted/stopped tasks.

**Regression test:** Cover old-owner delivery and handoff after a replacement claim, late updates after stop/accept, and a stale session using the same role name. Assert that rejected operations leave task state, references, and messages unchanged.

### F4 — P2: Ticket execution has no atomic ownership; the launcher can undo completion

**Location:** [reviews.py:198](/home/yu/workspace/smooth-research/src/smooth_research/reviews.py:198), lines 198–208; related unclaimed execution at lines 237–277 and unconditional completion at lines 356–365.

**Problem and execution path:** `_spawn` starts the subprocess before recording `status="running"`, then unconditionally overwrites the ticket. Independently, `run_ticket` reads a snapshot and checks `answered` without claiming execution under a write lock. Two workers can therefore both call a model, and each later replaces `calls` from its own stale list. Both review and advice dispatch use these paths.

**Observed evidence:**

1. With an already answered ticket, schedule the real child CLI to finish before the parent's state write. The child exits 0 with `RV-0001 already answered (pass)`; the parent leaves the ticket `running` with a `pass` verdict and no live worker.
2. Run two `run_ticket` invocations concurrently, synchronizing only the fake model boundary. Both invoke the adapter and both emit answer events, but the final ticket contains **one** call record: `adapter_calls=2, answer_events=2, recorded_calls=1`.

**Disproof checks:** This is not concurrent advice to different tickets. The existing `run_many` test (`tests/test_reviews.py:326`) covers distinct tickets. `show` only prints “worker not running: run again” (line 457); it does not restore the completed state. `review_passes` requires `status="answered"`, so the regressed ticket ceases to count as a passing review. The reproductions used a real child CLI/real database; model responses were stubbed and incurred no provider calls.

**Impact:** Duplicate provider work can incur duplicate cost, call accounting is lost, and a valid answer can be hidden behind a false running state. Retrying is not reliably idempotent.

**Recommended fix:** Claim a ticket atomically before launching or calling a model. Pass an execution identity to the child and accept status/answer updates only from the current claim. Keep completed tickets idempotent; record each call durably without replacing another worker's history. Recover abandoned claims explicitly.

**Regression test:** Same-ticket concurrent execution, a child finishing before launch bookkeeping, repeated background execution of an answered ticket, and an old worker completing after recovery assigns a new claim.

### F5 — P2: Conclusion-review coverage ignores the hypothesis being decided

**Location:** [research.py:320](/home/yu/workspace/smooth-research/src/smooth_research/research.py:320), lines 320–322 and 348–355; applied in `decide` at line 407.

**Problem and execution path:** `conclusion_reviews` selects cited tickets solely by `subject="conclusion"`. `review_gap` accepts any passing ticket. Neither compares the ticket's recorded targets with the decision's hypotheses. `attention` at line 520 and `view.conclusion_checks` at lines 174–178 reuse the same logic. The target edges are actually recorded by `request_conclusion_review` at lines 769–770.

**Observed evidence:** Review a proposal for H-0001 and import a passing answer. Then set unrelated H-0002 to supported through a decision citing that ticket. Observed:

```text
conclusion_review_gap = None
attention = []
report annotation = conclusion review RV-0001 pass (cross_model_unverified)
```

The ticket's target remains H-0001.

**Disproof checks:** This is independent of model-family requirements; the current contract intentionally does not require a particular relation. Correct-target and missing-review cases are tested at `tests/test_reviews.py:415` and `:434`, but unrelated targets and partial coverage of a multi-hypothesis decision are not. Request deduplication by package content does not validate a ticket subsequently cited by an arbitrary decision.

**Impact:** A decision is presented as independently reviewed even when the reviewer never evaluated its hypothesis. The warning that should guide the coordinator disappears from status and generated documents.

**Recommended fix:** Evaluate coverage for each decided hypothesis against the cited review's targets and recorded reviewed revision/snapshot. Keep unrelated tickets as historical citations if desired, but do not count them as coverage. Use the same coverage function for decision feedback, attention, and projections.

**Regression test:** A passing review for H1 must not clear H2's warning; a review of H1 alone must not cover a decision on H1 and H2. Add a revision-change case with an explicit expected freshness policy.

### F6 — P2: Assignment can bind a task to the losing worker's Git branch

**Location:** [agents.py:426](/home/yu/workspace/smooth-research/src/smooth_research/agents.py:426), lines 426–431, following the non-reserving check at lines 406–414.

**Problem and execution path:** `assign` permits an unclaimed task for any researcher and writes that session's branch into `Task.branch`. It does not reserve ownership. Two sessions can thus be assigned before either runs `task claim`. The successful claim later sets owner fields without correcting the branch. Task acceptance uses `Task.branch` to tell the coordinator what to merge (`tasks.py:245–247`).

**Observed evidence:** With real temporary Git worktrees and mocked herdr startup:

1. Open Alice on T-0001; open Bob on the same still-ready task.
2. Alice claims T-0001, commits an implementation on her branch, and delivers.
3. Accept the task.

The task owner was Alice, but its branch was `sr/bob/T-0001`. Acceptance reported:

```text
T-0001 -> accepted; branch sr/bob/T-0001 has nothing main lacks (merged, or no commits)
```

Alice's actual branch still had **one unmerged commit**.

**Disproof checks:** No simultaneous database access is necessary; merely delay both agents' initial claims. The one-winner claim guard works and still leaves the wrong branch. `tests/test_agents.py:162` verifies worktrees and merge guidance for a single assigned researcher, not multiple pre-claim assignments.

**Impact:** Acceptance can point to the wrong implementation or falsely indicate there is nothing to merge. The correct work remains outside the main branch without the expected merge guidance.

**Recommended fix:** Establish one transactional task/session/branch binding across assignment and claim, and preserve the winning task's branch as its delivery provenance. Revalidate state after Git operations before committing assignment records. A second pre-claim assignment must not be able to leave the eventual owner associated with another worker's branch.

**Regression test:** Two assignments before the first claim, followed by a real commit/delivery/acceptance; assert that acceptance names the winning owner's branch. Also cover reassignment after a legitimate handoff.

### F7 — P2: Explicit source-result rejection does not flag its scientific dependents

**Location:** [runs.py:414](/home/yu/workspace/smooth-research/src/smooth_research/runs.py:414), lines 414–420.

**Problem and execution path:** `reject_result` marks the Result rejected/unusable and updates the Attempt's aggregate status, but does not inspect incoming `from_result` or `based_on` dependencies. `research.add_evidence` checks source usability only at creation. A later rejection therefore leaves existing valid evidence and its decisions unchanged. `context.advice_pack` selects “Key valid evidence” solely by evidence validity (lines 196–200); `attention` does not discover rejected source results.

**Observed evidence:** Complete result → valid confirmatory evidence from that result → passing conclusion review → supported decision citing the evidence and review → reject the sole source result with reason “wrong labels”. The result became rejected, while:

```text
Evidence.validity = valid
Hypothesis.evidence_status = supported
Decision.needs_recheck = false
attention = []
```

The evidence still appeared in the advice package's valid-evidence section, and the decision retained its passing-review annotation.

**Disproof checks:** Explicitly invalidating the Evidence does propagate recheck flags (`research.set_evidence:290–306`, tested at `tests/test_records.py:115`). Rejecting the Result never invokes equivalent dependency checking. The workflow explicitly offers `run reject-result` when the result itself is wrong. Scientific validity remains a human judgment: this finding calls for a **recheck warning**, not automatic reversal of scientific support or automatic invalidation of diagnostic evidence.

**Impact:** Discovering and recording a bad measurement does not alert later readers that an existing conclusion relied on it. A coordinator or advisor can continue from a stale conclusion despite the ledger containing the reason to reconsider it.

**Recommended fix:** Propagate or derive recheck requirements through direct Result-based decisions and Evidence sourced from the Result, then to their affected conclusions. Surface the rejected source in evidence projections. Preserve the historical evidence/decision and require an explicit scientific reassessment.

**Regression test:** Reject the only source after a reviewed decision; verify warnings for precisely its dependents, no warning for unrelated hypotheses, and correct handling of evidence with other independent sources.

### F8 — P2: Literature links cannot advance their assessment or bind to a new hypothesis revision

**Location:** [store.py:199](/home/yu/workspace/smooth-research/src/smooth_research/store.py:199), lines 199–201; caller [literature.py:184](/home/yu/workspace/smooth-research/src/smooth_research/literature.py:184).

**Problem and execution path:** `Tx.link` treats a repeated revision-bound edge as a no-op when its `revision` matches. Literature links bind the *source* hypothesis via `source_revision`, with no target `revision`. Thus both comparisons are `None`, even when the hypothesis has changed. Repeating a link with a stronger assessment/locator is also silently discarded. `link_paper` nevertheless records an event and returns a success summary describing the requested new assessment.

**Observed evidence:** Link H-0001@1 to P-0001 as `nearest_work/search_hit`; relink as `checked` with locator `section 3`; revise the hypothesis to @2 and relink as `checked` with locator `section 4`. The commands succeed, but the graph contains only:

```json
{"rel":"nearest_work","id":"P-0001","source_revision":1,"assessment":"search_hit"}
```

There is no locator and no edge for revision 2.

**Disproof checks:** The relation is explicitly revision-bound in `schema.py:163–164`. The generic `research.link` also passes `source_revision` for citing hypotheses and encounters the same deduplication. `paper access` changes the Paper's access metadata, not these edge properties; there is no public link-update/unlink operation that completes the assessment workflow. Target-bound evidence relinking is tested (`tests/test_records.py:110–112`), but source-bound literature relinking is not.

**Impact:** A researcher can believe a claim has been checked and cited at the new revision while context/manuscript projections retain the old assessment. Provenance and locators are silently lost.

**Recommended fix:** Make revision identity explicit for both source-bound and target-bound relations. Provide a deliberate assessment/locator update or append-with-history operation for an existing claim revision, and return what was actually persisted. Projections should distinguish older hypothesis revisions.

**Regression test:** Search hit → checked on the same revision; relink after hypothesis revision; preserve old revision provenance; repeat identical input without adding duplicate edges.

## Architecture quality and simplification opportunities

**Keep the durable core.** Immutable document objects, explicit RunSpecs/attempts, imported observations, request deduplication, provenance records, and main-project/worktree separation form a sensible basis. The executor-independent boundary is appropriate. The findings do not justify an executor framework, a different database, or a wholesale rewrite.

**Consolidate semantic decisions.** Result completeness versus selected metrics (F1), comparison identity (F2), and conclusion coverage (F5) should each have one small authoritative computation. Review and manuscript generation currently consume presentation helpers from `view.py`; moving the shared fact-selection logic to a domain-level query helper would let presentation remain a thin consumer and remove some local-import/circular-dependency pressure.

**Consolidate lifecycle ownership.** F3/F6 show that Task.owner, Task.branch, and Session.assignment/branch are maintained by separate operations. F4 shows the same problem for ticket status, PID bookkeeping, and call history. Prefer a small explicit transition/claim API over adding independent defensive checks to every caller. Remove superseded mutation paths once the ownership rules have one home.

**Give revision-bound edges a precise meaning.** The single `revision_bound` boolean hides whether the source or target is versioned (F8). Making that distinction explicit is smaller and clearer than paper-specific exceptions scattered through link callers.

**Retain documented compatibility until migration is deliberate.** Old model configuration shapes, legacy plan/constraint paths, and pre-severity/pre-scope review records have documented and tested behavior. They are not established dead code merely because new projects do not generate them. A future migration can normalize old persisted/configuration data and then delete the associated readers; deleting them now would change supported behavior. No large subsystem was proven unused.

**Do not turn unmeasured scale concerns into defects.** Package/report generation performs repeated graph reads and document work while holding shared locks; at large histories, read duration can affect writer latency. This warrants a representative history benchmark if that scale is expected. This review did not establish a production-size bottleneck. Duplicate model work in F4 is an already demonstrated resource problem.

## Missing tests and rejected candidates

The most valuable additional tests are the cross-boundary sequences attached to F1–F8. In particular, assert rendered values and provenance, not only aggregate statuses; exercise an old worker after ownership changes; force deterministic scheduling around process launch and final writes; and test source-bound revisions separately from target-bound revisions. Real host integration smoke tests and a larger-history benchmark would add evidence beyond the current fake-host coverage.

Several plausible concerns were excluded from the findings after checking the contract:

- Results may arrive before execution ends, and diagnostic evidence can describe a failed run. Those are intentional independent facts.
- Missing/unknown RunSpec provenance is permitted and reported. F2 concerns supplied contradictory values.
- Descriptive means are explicitly over attempts, not claimed to be independent seed-level inference.
- Code-review reuse is intentionally about the specified code/config/dependency scope; changing only a scientific contract is not by itself proof that a code review must become invalid.
- Snapshot restore is a records/sealed-object recovery operation, not a full reconstruction of code checkouts, mutable drafts, or external jobs. Missing working files after restore were not reported as data loss.
- Codex review permissions follow the configured host behavior documented in `docs/configuration.md`; absence of a forced read-only sandbox was not treated as an accidental regression.

**Overall assessment:** The design is recoverable with focused changes. Prioritize F1–F3 for scientific-output and ownership integrity, then fix ticket claims and the provenance/assignment paths. The passing suite is meaningful evidence for the persistence substrate, but it does not yet establish the end-to-end invariants needed for reliable parallel research work.
