F1（P1）：标准项目环境无法启动后台审查和委派进程

位置：`src/smooth_research/reviews.py:208–215`，`src/smooth_research/delegate.py:175–187`；相关启动边界为 `plugin/bin/rl:180–185`。

问题与调用链：项目启动器通过项目 `.venv/bin/python -I -c ...` 启动，并在当前解释器内把插件的 `src` 加入 `sys.path`。该项目环境安装的是 rl 所需依赖，并没有安装 `smooth_research` 包。后台审查、建议和委派却使用 `sys.executable -m smooth_research` 新建解释器；父进程对 `sys.path` 的修改不会传递到子进程，所以正常前台命令可运行，后台 worker 仍然无法导入包。委派附带的 `SMOOTH_RESEARCH_RL` 也不能修复 worker 自身启动前的模块导入。

复现与证据：在临时目录中，用真实 `plugin/bin/rl` 初始化全新项目，清除继承的 `PYTHONPATH` 和相关项目环境变量，使用独立工具缓存目录。创建代码文件和审查票据后，执行 `review run RV-0001 --background --entry manual:reviewer --json`。父命令退出码为 0，返回 worker PID 和日志路径；日志随后显示：

```text
<临时项目>/.venv/bin/python: No module named smooth_research
```

直接使用该 `.venv/bin/python -m smooth_research --help` 同样失败。复现使用 manual entry，没有实际调用模型。错误发生在 worker 进入票据处理逻辑之前，因此不能依赖票据中的调用失败处理来发现它。

影响：使用受支持的项目环境安装方式时，后台审查、后台建议以及后台委派无法开始工作，父命令的成功返回也不能说明 worker 已运行。对于另外安装了包的解释器，此问题可能被遮蔽；这不否定标准初始化路径中的失败。

反证与测试缺口：`tests/test_setup.py:46–66` 验证了项目环境启动器；`tests/test_reviews.py:787–799` 的 worker 测试替换了 `Popen`，再在当前测试进程中执行参数，因此没有经过新解释器的导入边界。这两部分分别通过，不能验证两者组合。

建议：让两处后台入口复用与前台一致的可导入启动方式，例如已解析的 rl 启动器或明确携带插件源码位置的解释器引导，集中维护这段命令构造；同时让启动失败能被调用方可靠观察。添加一次从真实 `rl init` 创建的项目环境启动真实子进程的回归验证，可使用 manual entry 或假的外部模型命令，不需要付费调用。

F2（P1）：不同环境的实验结果被合并成同一比较条件并求均值

位置：`src/smooth_research/view.py:106–112`、`:132–150`、`:156–170`。结果验证中的相关字段见 `src/smooth_research/runs.py:26–27`；既定工作流语义见 `plugin/skills/smooth-research/references/workflow.md:122–124`。

问题与调用链：`condition()` 只包含合约版本、arm、数据、模型、配置和参数，没有 `environment_ref`。`arm_rows()` 用这个条件对象分组并计算均值，显示条件差异时也不包含环境。但运行规格和结果比对已经把环境作为比较维度，工作流明确要求不同 `environment_ref` 不视为同一比较。共享表格用于报告、HTML 解释页、论文和结论审查包，因此不是单一页面的显示瑕疵。

复现与证据：通过公开项目与运行 API 创建同一实验下的两次运行，除 seed 和环境外，其余比较条件一致。两个环境分别为 `lock-a,cpu` 与 `lock-b,cuda`；各自接收与自身 RunSpec 完全匹配的完整结果，运行均为 `ended/success`，指标 `acc` 分别为 0.1 和 0.9。调用 `arm_rows()` 得到一行：

```text
condition: ''
seeds: '0,1'
attempts: '2 ended/success'
cells: ['0.5 (n=2)']
notes: ''
```

两个不同环境的结果既被平均，又没有环境差异提示。结果校验不能挡住这种情况：每个 manifest 都与自己的 RunSpec 一致，问题发生在后续跨运行汇总。

影响：自动汇总会把按项目约定不可直接视为同一条件的数据展示成一个均值，影响研究者、论文读者和结论审查模型对证据的判断。`explain.py:576–592`、`manuscript.py:218–225` 以及 `reviews._conclusion_body()` 使用同一表格逻辑，传播范围大于单个命令。表格说明均值是描述统计，也不能纠正错误的条件划分。

反证与测试缺口：`tests/test_explain.py:211–238` 已覆盖合约、数据、代码版本和 seed 的分组行为，但没有两个有效结果仅环境不同的用例。这里也没有把按约定允许不同的 seed、代码提交或输出位置误判为必须分组的字段。

建议：把环境身份纳入比较条件和差异展示，并根据明确的科学比较语义核对 RunSpec 校验、聚合和呈现使用的字段。新增回归验证：不同环境必须分成两行且不能生成混合均值；同一环境下不同 seed 仍按现有约定聚合。

F3（P1）：迁移保护漏掉受保护目录的祖先路径，可搬走正在使用的数据库

复现与证据：在独立临时项目中完成初始化、创建假设，再调用 CLI `upgrade --move` 对应的公开实现 `upgrade.move(store, 'research', 'archive')`。得到成功结果：

操作返回成功，但正常项目入口随后无法找到数据库。此复现仅操作临时项目，没有移动真实仓库或用户项目的数据。

影响：合法接受的迁移参数使项目失去正常可读性，需要人工移回文件或恢复备份；存在封存文档时，它们也属于被移动的目录树。已确认的是固定路径与持久化文件脱离，并非已证明文件字节被销毁。错误提示引导重新初始化也无法恢复原数据库位置中的记录。

F4（P2）：迟到的自动 worker 失败会覆盖已经完成的人工审查

位置：`src/smooth_research/reviews.py:302–307`；相关路径为 `:255–264` 的 worker 认领、`:292` 的外部调用、`:394–403` 的人工导入和 `:362–371` 的答案写入。

问题与调用链：worker 先认领票据，释放事务锁后调用外部模型。期间允许人工导入或其他合法渠道提交答案。自动调用最终失败时，它用开始时保存的票据与 calls 计算结果，并无条件把状态写成 `unavailable`、`failed` 或 `pending`，没有在写事务中重新检查票据是否已经回答。数据库事务可以串行化单次写入，却无法让这次过时的状态转换变得正确。

复现与证据：使用本地同步事件暂停假的 `adapters.call()`，启动 `run_ticket()` 后在调用尚未结束时导入一个独立模型的 pass 答案，再释放事件让原调用返回失败。没有实际模型请求。两次检查结果为：

```text
自动 worker 结束前：status=answered，answer_ref=DOC-0002@1，review_passes=True
自动 worker 结束后：status=unavailable，answer_ref=DOC-0002@1，review_passes=False
```

复现通过事件控制顺序，不依赖随机 sleep。答案引用仍然存在，但有效性被迟到的失败撤销。

影响：慢调用、超时或服务异常期间采用人工回退，本来已经通过的审查会失去覆盖资格，任务和研究记录会重新表现为未完成审查，可能引发重复工作与调用。此缺陷的已证实方向是有效答案被失效，不是未通过的审查被错误放行。

反证与测试缺口：`_worker()` 能阻止两个自动 worker 同时认领，但人工导入不受这个认领检查约束；`tests/test_reviews.py:750` 附近的进程占用测试覆盖了 worker PID 与复用判断，没有覆盖自动调用与人工提交交错完成。

建议：在最终写事务内重新读取状态并核对本次 worker 的所有权，确保 review 一旦接受答案就不会被迟到结果退回。迟到的调用日志可追加记录，但不应覆盖已接受的答案状态。应同时检查其他答案入口的终态检查与写入是否处于同一事务；保留 advice 明确支持修订的独立语义。新增确定性的并发回归：调用阻塞期间导入 pass，之后让调用失败或成功返回，已接受答案及其审查资格都应保持不变。

F5（P2）：多个低额度窗口剩余百分比相同会抛出 TypeError，阻断额度相关流程

位置：`src/smooth_research/usage.py:204–208`；下游包括 `agents.list_sessions()`、条目选择中的 `usage.low_hosts()`、`reviews.run_ticket()` 和 `watch._Beat`。

问题与调用链：代码通过 `sorted((left(w, now), w) ...)` 选择最低剩余额度窗口。两个窗口的剩余百分比相同时，Python 会继续比较元组第二项；第二项是 dict，无法排序，于是抛出 TypeError。两个周期都耗尽、都剩同样百分比是正常输入，不是损坏缓存。

复现与证据：使用独立缓存目录，通过真实 `usage.statusline()` 输入 Claude 的 five_hour 和 seven_day 窗口，两者 `used_percentage=100`，重置时间均在未来。状态行正确显示：

```text
5h 0% left · week 0% left
```

随后调用 `usage.hosts(store)` 得到：

```text
TypeError: '<' not supported between instances of 'dict' and 'dict'
```

该错误也适用于进入相同标准化窗口结构的其他 host。触发条件是至少两个未过期、达到低额度阈值的窗口具有相同剩余百分比；不是任意两个窗口相等都会进入这段排序。

影响：会阻断会话列表、自动 host 选择、审查回退和 watcher 的额度检查。watcher 在 `watch.py:291` 构造读取结果，运行循环 `:845–848` 只捕获 `RLError`，不会把该 TypeError 当成可处理的状态错误；恰在需要自动切换 host 的耗尽场景，自动编排可能直接退出。

反证与测试缺口：已有多个窗口的读取测试和阈值测试，但其百分比不同或只有一个低窗口，没有覆盖并列低值、尤其双窗口同时为零的边界。

建议：使用只比较数值的显式 key 选择最小值；若要固定同值行为，可增加窗口名称等可比较的稳定次序，不要比较窗口对象本身。回归覆盖两个低窗口同值、同时耗尽，以及 stale/reset 语义仍然正常，并验证上层 host 选择不抛异常。

F6（P2）：`--read-only` 在创建只读 Store 之前仍会写配置缓存

位置：`src/smooth_research/project.py:539–542`，`src/smooth_research/cli.py:57–60`；只读约定见 `cli.py:44–54`。

问题与调用链：CLI 先执行 `find_project()`；其配置读取会在 `research/state/config.last-read.json` 缺失或与当前 YAML 不同时调用 `atomic_write()`。此后才构造带 `read_only=True` 的 Store。只读命令白名单和 Store 的只读打开方式都不能约束发生在前面的配置副作用，而 CLI 明确承诺只读命令不写文件或缓存。

复现与证据：在临时项目中初始化并读取配置，使缓存存在；记录缓存字节，再把有效 YAML 中的 `max_rounds: 3` 改为 `max_rounds: 4`，执行：

```text
rl --project <临时项目> --read-only status
退出码：0
config.last-read.json 的字节发生变化：True
```

这里主动修改 YAML 是测试前置条件，真正违反只读约定的是随后 status 命令更新了缓存。缓存不存在而父目录存在时也进入同一写入分支。

影响：审计、诊断或明确要求只读的调用仍改变项目文件，也改变下次配置解析失败时使用的持久化回退值。即使数据库没有写入，这仍违反公开只读行为。

反证与测试缺口：`tests/test_upgrade.py:276–302` 的只读文件对比使用了已经缓存、没有变更的配置，因此没有进入写分支；启动器的只读环境测试也不覆盖配置缓存刷新。

建议：在项目发现和配置加载之前传递只读意图，或把纯配置解析与更新回退缓存分离。补充两个真实 CLI 回归：有效 YAML 已变化、缓存缺失；执行只读命令后文件系统应不变，同时命令仍应读取当前有效配置。

| `reviews` / `tasks` / `agents` / `watch` | 审查范围与覆盖、任务认领与交付、外部模型和进程生命周期、额度切换 | 有明确的认领和回退机制；进程导入、外部调用后的终态提交以及额度边界仍存在 F1、F4、F5。 |
| `view` / `explain` / `manuscript` / 上下文 | 从研究记录生成共享事实和表格，保留用户叙述并控制上下文规模 | 复用事实生成逻辑有价值，也会扩大聚合错误的传播面。 |
| 快照、迁移、插件构建与计算配置 | 可恢复存储、版本升级、共享插件与薄 host 适配、源码同步及执行说明 | 已有恢复和构建测试；真正外部运行仍需要单独集成验证。 |

简化与删除机会应围绕已证明的边界问题展开。两处后台入口可以共用一个启动构造，避免解释器与代码来源的规则散落；配置读取与缓存写入可以明确拆分；运行比较条件应有一处明确的语义定义供汇总使用；票据最终写入应集中执行状态与所有权检查。这些调整分别对应 F1、F6、F2、F4，可以减少重复规则而无需引入通用调度框架或重写存储层。

没有发现足够证据支持大规模删除旧 schema 迁移、已有快照兼容路径或仍被 CLI 使用的工具功能。旧版本 fixture 和现有调用证明这些路径仍服务明确契约。设计目录是事前参考，不因实现偏离设计文本就单独报错；本次也没有把已明确允许的本地论文编译行为列为资源政策问题。未测得可量化的性能或规模瓶颈，因而不把可能的查询优化包装成已证实的性能缺陷。

最有价值的测试补充是：真实启动器到真实后台进程的组合测试、不同环境的有效结果分组、受保护目录祖先拒绝、人工答案与自动完成交错、多个低额度窗口同值，以及变更配置后的只读文件不变性。它们分别守住真实集成边界、领域约束和确定性失败路径，优先级高于增加纯实现细节断言。
